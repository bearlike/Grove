# grove.core.runtimes — serverless drivers for remote workspaces

> ↑ [core](../CLAUDE.md) · [root](../../../../CLAUDE.md)

One module per platform, each a class satisfying `ServerlessDriver` and configured from its `runtimes.<name>` block (`config.py`, a `kind`-discriminated union). The per-platform verdicts, limits and sources live on the epic's design comment, not here.

- **A driver shells out through `_cli.ProviderCli` and nothing else; no provider SDK is a dependency.** `call` returns `None` for "could not run" and a `CliResult` for any answer, a non-zero exit included, so `status` can tell "the platform says the execution is gone" (`ABSENT`) from "nobody answered" (`None`). The driver reads the platform's own error words (`NOT_FOUND`, `RESOURCE_EXHAUSTED`) at that edge and nowhere else.
- **A REST driver never repeats a raw response body (`_http.response_detail`).** A server's validation error routinely echoes the request it refused, and the request is where the worker bearer and a registry password ride: OpenSandbox's FastAPI 422 put both on stdout on the first live create (#1051). Only `message`, `detail[*].msg` or a string `detail`/`error` are read, else `<status> <reason>`; `input` and `response.text` never. Every REST driver routes through it. A refused create also revokes the worker bearer it minted, in the rollback's `container` inverse, because the mint precedes the `up` that refused.
- **A `*_env` read goes through `_env.RuntimeEnv`, which refuses an unset or empty variable naming it and the dotted path (`runtimes.<name>.<field>`), before any I/O (#1049).** Read as `""`, an unset `url_env` became a relative base URL and the user saw httpx's "missing an 'http://' protocol"; an unset password reached the server as an empty credential. Same rule as `EnvReferences` for `${VAR}`: naming a variable is the opt-in, and `optional()` treats only an EMPTY field as off. **The CLI drivers' credential names (`credentials_env`, `access_key_env`/`secret_key_env`, `client_secret_env`) deliberately stay soft**: they default to the provider's own variable, and an unset one leaves `gcloud`/`aws`/`az` on its ambient credential chain, so refusing would break working ambient auth. A driver's test module sets every variable its `_CFG` names in an autouse fixture, and a refusal test deletes the one it leaves unset.
- **A quota or capacity refusal raises `ProvisionRefused` on the first answer and is never retried**; the test asserts exactly one CLI call.
- **The handle is the only durable state.** `thaw` on a no-suspend platform re-reads the frozen execution's own overrides from the platform and re-executes with `GROVE_RESUME=1`, so nothing beyond `RemoteHandle` needs persisting and a daemon restart between freeze and thaw loses nothing. An execution the platform has already forgotten cannot be thawed and says so; the remedy is a fresh `up` from the branch.
- **"Frozen" on a no-suspend platform is Grove's persisted fact (#970); the driver only observes STOPPED.** Conformance therefore accepts `FROZEN`, or `STOPPED` when `thaw` returns a new handle, derived from what the driver does rather than a declared capability.
- **`rm` may leave an execution readable as STOPPED, never running.** ACA keeps ended executions as history and offers no delete, so its `rm` is its `stop`; conformance accepts ABSENT or STOPPED after `rm`. ACA history keeps only the latest 100 executions, so status is always read by execution NAME.
- **OpenFaaS `stop` and `freeze` are both zero replicas to the platform, so the function carries a `grove.state` label saying which**, written by the same redeploy that sets the replica bounds. The function is the only thing that survives a daemon restart, so it is the only honest place to keep that fact. Its thaw keeps the handle: same function, cold restart, resume from the branch.
- **A driver that speaks REST takes an injected `httpx.Client` instead of `ProviderCli`** (OpenFaaS: its gateway API is the documented verb surface and `faas-cli` cannot read a function's replicas as data); tests swap in `httpx.MockTransport`. httpx is already a base dependency.
- **A Lambda MicroVM is launched with the `NO_INGRESS` connector and NO idle policy.** It ships with a public endpoint by default, and the platform's idle suspend keys on endpoint traffic, which a dial-out worker never produces, so leaving it on would suspend a busy agent. Per-workspace facts ride `--run-hook-payload`, because image-level env is shared by every MicroVM of an image. Its freeze/thaw is native and keeps the handle; its stop terminates, since a MicroVM cannot restart.
- **OpenSandbox has no stop that keeps a sandbox: `stop` and `freeze` both PAUSE it, and a `grove.state` metadata key (PATCHed BEFORE the pause, so it never reads Paused under the wrong name) says which.** Same shape as OpenFaaS's label, same reason: the sandbox is the only thing that survives a daemon restart. Resume keeps the sandbox id, so thaw keeps the handle; on the Docker backend a pause is `docker pause` (memory resident, lost on a host reboot), so a thaw that finds the sandbox gone RAISES. `WorkspaceManager.thaw` turns that into a fresh workload on the pushed branch when (and only when) the platform confidently reports the workload ABSENT, for every driver: the driver holds no spec to re-`up` from, and the manager's respawn already composes one. A thaw that fails while the workload still lives stays frozen and raises. The API lives under `<url>/v1`; a private image's registry credential (`image_auth_*_env`) rides the create body only, with the bearer's discipline. Its create request is the only one carrying the worker bearer as a VALUE (in `env`, over the API's private channel; `emit_spec` omits it), and its `networkPolicy` is explicit deny-by-default with allows for exactly `WorkspaceSpec.reach` (daemon + git remote) plus `allow_hosts`: never rely on the server's default. Each name is emitted WITH its IPv4 addresses resolved at create (`_two_layer`, injectable `resolve`): a dns+nft server lets a name resolve and then drops the connect, so a name-only allow blocked the worker's own clone (#1055). An unresolvable name stays name-only and logs; `0.0.0.0` is never an allow; an IP or CIDR passes through. 403 (quota) and 429 (pool capacity) are `ProvisionRefused`.
- **The emitted spec is JSON**, which every YAML reader (`gcloud ... replace`, `az ... --yaml`, `faas-cli`) accepts, so PyYAML stays a test-only dependency. Secrets appear only as platform secret references (`WORKER_TOKEN_ENV` via `secretKeyRef`), never as values; `WorkspaceSpec.env` is plain configuration by contract.
- **Tests fake the CLI by subclassing `ProviderCli` and interpreting argv in memory** — the driver takes the edge by injection, so no `subprocess` patching is needed and no test can reach a real cloud.
- **A REMOTE workspace's post-launch answers are `workspace_runtime.RemoteRuntime`, a sibling of `ContainerRuntime`/`HostRuntime`; this package only supplies `factory.build_driver` (one `kind` → one class).** The record carries `WorkspaceState.remote: RemoteHandle`, decoded loudly like `container` because a dropped handle orphans a billed workload. Liveness and teardown go through the driver; `attach_instruction` and `worktree_reader` refuse (`CapabilityUnavailable`), since no local pane or path reaches the workload. `WorkspaceDefaultsView.runtime` stays host/container because a saved default nobody can create from would be a lie on every create form; the remote choices ride `WorkspaceDefaultsView.targets` instead. **One user-facing runtime name means `host`, `container`, or a block name, and `CreateWorkspaceRequest.runtime_fields` is the one parse** the CLI's `--runtime`, the MCP tool and the TUI picker share, so no shell guesses whether a name exists; the engine's admission refuses an unknown one, naming the configured set.
- **F5 is code: `stop` and `freeze` PUSH the branch through the worker (`git push origin HEAD:refs/heads/<branch>` on the read channel) before ending or suspending the workload, and a failed or unreachable push raises and leaves it running.** The branch is the only state that outlives a workload, so "could not push" must never degrade into "ended anyway". Only COMMITS survive; uncommitted work in the workload is lost on a no-suspend platform, and that is the agent's contract, not something Grove papers over. `thaw` returns the new handle a fresh-execution platform hands back and `WorkspaceManager.thaw` persists it.
- **Create onto a remote runtime is admitted before any side effect** (`WorkspaceManager._admit_remote`): a resident `runtimes.<name>` (the request's `remote_runtime`, or the only one configured), a native agent, `daemon.mailbox_url` and a git remote, because a workload missing any of them is one nobody can reach. The local worktree and branch are still created as the record's anchor (kill and rollback stay unchanged), init never runs (the agent's tree is the workload's clone), and the workload's stage is `container`, so a refused `up` unwinds through the runtime teardown.
- **The worker boots from `GROVE_WORKER_CONFIG` (its whole `NativeWorkerConfig`) and clones the repo itself** — the pushed branch if the remote has it, else the branch at `base_commit` — so nothing dials in and nothing is mounted. Its per-workspace bearer (`worker_label`, revoked by `kill`) rides `WorkspaceSpec.secret_env`, which a driver sends only on a private channel to the platform and never into `emit_spec`, an argv, a log or `repr`; a CLI-only driver ignores it and uses the platform secret its `*_env` config names. An env over the platform's documented limit refuses whole (`require_env_within`, Cloud Run 32 KB); a cut worker config would boot nothing.
- **The sandboxed agent's environment is `_launch_env`, the same composition every host and container launch uses, carried on the spec by ONE rule**: a value equal to what the operator wrote in `AgentSpec.env` is a config literal and rides `env`; everything else (telemetry keys, proxy tokens, anything resolved from a `*_env` name or this process's environment) rides `secret_env`, because it may be a credential nobody chose to publish. A `${VAR}` reference in `AgentSpec.env` is NOT a literal: the cascade leaves agent env as its template, so `AgentSpec.deferred_env()` names those keys straight off the spec and `launch_env` supplies their values, which then ride `secret_env` (#1057). No per-variable table. The phase path is dropped (it is a host path; the worker publishes its own). Before this the worker got only its own config and the agent booted with no provider URL or key (#1054, found by the live smoke, not by any test).
- **A remote respawn MINTS a fresh session on the pushed branch, it does not resume.** The transcript lives in the workload's home directory, not on the branch, so a fresh workload has nothing to resume and `--resume` on a missing id fails the launch. Durable remote resume needs the transcript to survive (native pause, or syncing it) and is its own ticket. Respawn pushes first while the worker answers and refuses on a failed push unless the platform already reports the workload gone. `GROVE_RESUME=1` on a thawed fresh execution makes the worker drop the initial task, since replaying it would restart work already in progress.
- **HIBERNATE is a third sibling Protocol (`HibernatingDriver`: `hibernate`, `wake(handle, spec)`, `forget`), never a widening of `ServerlessDriver`; a runtime without it simply stays frozen.** Three decisions carry it. **`wake` takes a fresh `spec`** because the handle is `(runtime, ref)` and the worker bearer must never be persisted, so no handle can carry everything a re-create needs; the manager re-composes the spec through the same `_remote_spec` create uses, minting a new bearer, and conformance (`assert_hibernate_conformance`) wakes from the handle plus a fresh spec alone. **A hibernated ref is `snapshot:<sid>`**, and teardown routes it to `forget`, never `rm`. **`WorkspaceManager.thaw` checks `hibernated_at` BEFORE its ABSENT→respawn fallback**: a snapshot handle reads ABSENT as a sandbox, so the wrong order silently skips the snapshot and loses the session (mutation-checked). `frozen_at` stays set while hibernated, so every frozen reader works unchanged; the idle watcher's second rule (`IdleRule.hibernate`, `idle.hibernate_after_seconds`, 0 off) reads only the frozen stamp, and a thaw restarts it by clearing that stamp. Wake RESUMES the pinned session, because the snapshot keeps the worker's home and transcript (unlike a #1028 respawn, which cannot); the worker skips its clone when `.git` already exists, and if the restored home has NO transcript for that id it swaps `--resume` for `--session-id` on the same id (`native_worker._resumable`) rather than failing the launch. That fallback is a remote-only decision taken where the transcript would live, because the daemon cannot see the workload's filesystem.
- **OpenSandbox hibernates through `docker` on the server's own engine, because its Docker backend keeps snapshots as local images only.** The server snapshots only a RUNNING sandbox (a paused one answers 409 `SNAPSHOT::INVALID_SOURCE_STATE`, found by the first live hibernate on 2026-10-22, release-1.1.1), so hibernate RESUMES the frozen sandbox first, and any failure, the sandbox delete included, drops the snapshot it made and PAUSES it again: a frozen sandbox never holds a snapshot, which is what lets the idle watcher's un-backed-off retry start each attempt from the same state instead of re-snapshotting a running worker. The worker runs for about two seconds with no prompt sent. That is accepted because the branch was pushed at freeze; **hibernate deliberately does not repeat the F5 push**, so do not add one there. The fake server refuses a paused source the same way, which is what makes the resume load-bearing in the tests (mutation-checked); a fake that snapshots any state is how this shipped. Then: snapshot → wait Ready → tag + push to the runtime image repository (or an explicit `snapshot_registry`) → delete the sandbox → drop both local tags. The `snap-<id>` tag lets an OCI registry reuse the runtime image layers. Wake pulls, retags to `opensandbox-snapshots:<sid>` and creates with `snapshotId` and no `image`; the record keeps that snapshot until the restored worker's first owner registration confirms it dialled in, then forgets it exactly once. A never-confirmed snapshot intentionally has no cleanup timer, because it remains the only recovery copy; a later hibernate deletes it before recording the newer snapshot, so one record never loses the last named copy. The registry credential rides a throwaway `docker --config` directory, never argv and never the user's own login; the registry delete is the generic OCI `HEAD` (digest) then `DELETE /v2/<repo>/manifests/<digest>`, with no forge-specific API.
- **EPISODIC is a sibling Protocol (`EpisodicDriver.run_turn`), never a widening of `ServerlessDriver`, and conformance asserts the driver is NOT also a `ServerlessDriver`.** Nothing runs between turns, so there is no handle, no `up`/`stop`/`freeze`, and freeze is free. Both kinds share the one `runtimes.<name>` namespace, split in `config.py` as `ResidentRuntimeConfig | EpisodicRuntimeConfig`, so `RemoteRuntime.driver` refuses a handle that names an episodic block (it holds no workload) and `factory` has one builder per model.
- **`TurnResult` is only ever decoded from the platform's answer (`TurnResult.from_wire`), never synthesised.** A turn cut short by the request deadline raises, because a made-up result would read as a turn that finished; the worker pushes what it had before it died, and the branch is the truth.
- **An episodic invoker credential is minted per turn by the provider CLI** (`gcloud auth print-identity-token --audiences=<url>`), so no SDK is needed and nothing long-lived is held; no token means no request. Who may invoke is IAM, outside the emitted document, which is why the spec carries no ingress claim.
- **`aws lambda invoke` reports a function error with exit status 0**: the payload goes to the outfile and `FunctionError` rides the printed metadata. Read the two separately (a temp outfile, never `/dev/stdout`), and test the guard with a fixture whose error has a message only that branch can produce, because otherwise `TurnResult.from_wire` rejects the error payload anyway and the guard reads as covered while deleted (mutation-measured).
- **A remote worktree is reached by asking the worker, never by translating an argv.** `WorktreeReader` (argv → argv run here) cannot express a worktree on another host, so `RemoteRuntime.run_in_worktree` takes a `WorktreeRunner` (argv → `WorktreeRead`). The daemon binds it to `OwnerSteerClient.run_in_worktree`, which puts a `read` frame on the owner's existing SSE channel: `NativeOwnerRegistry.read` holds one future per `read_<uuid>` request id, and the worker runs the argv bounded in its own cwd and POSTs `/mailboxes/read-result`. Three properties carry the design. **Opt-in**: an owner declares `reads=1` at registration, because an older worker queues an unknown op as prompt text (`live` set this precedent). **Never hang**: a timeout, a full queue and an owner leaving mid-read all raise `OwnerUnavailable`, and unregister fails every pending future. **Unreachable is no answer**: the command watcher returns no observation rather than a settled failure, since the worker may just be reconnecting. A read frame carries no `submitted` entry, so it can never release an input credit. A process with no daemon (the CLI) has no runner and refuses.
- **A REMOTE workspace's git and phase reads go to its worker through `WorkspaceManager.git_for(state)`, and every read site asks it rather than holding `self._git`.** `GitRepo(path, runner=…)` routes every INSTANCE read (`_exec`) to the runner, forwarding the call site's own `cwd`/`timeout`/`env` to `_run` unchanged on the local path, because tests patch `_run` with fakes of exactly that shape; the four classmethods (`detect_root`, `global_config`, `init`, `clone`) are never workspace reads and stay local. `git.py` defines its own `GitAnswer` protocol rather than importing `WorktreeRead`, so dependencies keep flowing inward. Local-directory short-circuits (`is_clean`, `dirty_file_count`) are skipped under a runner, since a remote worktree never exists on this disk. The phase file is read with `stat -c %Y` then `cat` (argv, no shell) and parsed by `PhaseFile.from_text`. **Unreachable is OFFLINE, not zero:** `RemoteRuntime.liveness` answers False for a workload the platform reports RUNNING while `owner_connected` says its worker is off the channel (STARTING is exempt, since a booting worker has not dialled in), so `_reconcile_status` demotes it and the dashboard never shows a confident zero for a worktree nobody could read. **A workload Grove started or woke within the boot bound is exempt too** (`RemoteRuntime._booting`: `max(created_at, thawed_at)` plus the roster's longest `native_timeout_seconds`), because the platform answers RUNNING long before the worker dials in (~110 s measured): read as OFFLINE, a message that had just woken a hibernated workspace auto-revived it, respawning from the pushed branch and discarding the restored session two seconds after the wake (#1076). Independently, `send_message` never revives a workspace the same call thawed (`_steer_woken`): it delivers if the owner is already here and otherwise refuses with a "waking, retry" 409, because a workload slower than the bound must not be destroyed either. Each guard has a test that only it can pass. There is no held-frame queue for an owner that has not registered yet; the registry refuses a steer with no binding at once.
- **A remote workload pushes with a credential that belongs to the git REMOTE, not the platform (`worktree.push_token_env`, #1068).** The worker clones anonymously, so the gap was invisible until the first live freeze: every F5 push answered `could not read Username`, and no remote could freeze, hibernate, stop or respawn against a forge that needs a login to push. Neither the smoke (it never froze) nor the unit tests (they stub the push) could see it. The token is resolved by NAME from this process's environment at admission, so a named-but-unset variable refuses before any side effect, naming the variable and the dotted path. It rides `secret_env` as `PUSH_TOKEN_ENV`, never `emit_spec`. The worker removes it from the agent's environment and hands it only to argv whose first token is `git` (`GitPushCredential.env_for`) through `GIT_ASKPASS`: a 0700 script in a private temp dir that prints the token for a password prompt and a fixed name for a username prompt, reading the token from its own environment so it never lands on disk, an argv or a URL. **Reusing `tickets.<forge>.token_env` was rejected as a coupling**: it works only while that tracker is enabled, and GitHub's `base_url` is its API host, which never matches the `github.com` git remote. The push test drives `NativeWorker._serve_read`, the real call site, against a smart-HTTP `git-http-backend` that answers 401 without Basic auth. A first version called `_run_bounded` directly and stayed green with the wiring deleted (mutation-measured).
- **A remote transcript tail is located BY THE WORKER, never addressed by the daemon.** Where a provider writes its transcript is a fact of the worker's own namespace (its home, its provider's config dir), so the daemon sends `{tail: N}` on the same `read` op and the worker resolves `get_adapter(provider).locate_transcripts(cwd, session_id)` itself; `(0, "")` means no session or no file yet. `WorkspaceManager.transcript_tail` reads the local file for every other runtime, and for REMOTE raises `PaneNotFound` on any non-zero answer, so "unreachable" can never be mistaken for "the agent has said nothing". Deliberately NOT done: routing the activity blend's transcript PARSING through the worker — those reads run per tick through every adapter's `TranscriptCache`, and doing them remotely is a protocol, not a seam.
- **A REMOTE workspace's agent axis is the hook SIDECAR, fed by its worker over the daemon connection (#1030), never a remote transcript parse.** The host spool a local owner drops into (`AskRecorder`) is unreachable from a workload, so a remote worker's recorder takes a `sink` and `NativeWorker._send_spool` posts each drop, in order, to `POST /mailboxes/spool`. The daemon writes it into the host spool, where `ClaudeHook.read` folds it exactly like a local drop, and admits a hook invalidation. Only a sink-built recorder states TURN EDGES (`UserPromptSubmit` when the provider echoes a root input, `Stop` on `result`), because a host or container session's hooks and transcript already say so and a second producer would double them. The blend then reads state through the ordinary `supersedes_poll`, and `last_event_at` is the sidecar's `ts`, the daemon's receipt of the newest edge, which is what lets `IdleRule.idle` pass and the freeze and hibernate tiers fire for a remote at all. Three properties carry it. **The fence**: bearer plus generation like `/pulse`, and a drop naming any session but the binding's own is 403, since a worker could otherwise write a stranger's agent state. **Unreachable outranks the push**: a REMOTE row reconciled OFFLINE ignores its sidecar (`ActivityService._remote_push`), or a dead worker's last `Stop` would hand the idle watcher a clock for a workload nobody can reach. **A lost edge is retried, not dropped**: a stale WORKING would hold for the sidecar window. The sessions listing names the remote session off the same sidecar, with path and size `None`, UNTIL the worker's first mirrored transcript chunk lands (next bullet); the sidecar is then corroboration, and the clock is the newer of the push and the parse (`_remote_clock`).
- **A REMOTE workspace's TRANSCRIPT is MIRRORED to the host by its worker, append-only, by byte offset (#1099), and that is what lets every host reader stay a file reader.** Measured 2026-10-23 on a live sandbox workspace: the card read `waiting`, the session had cost $2 and used 91k tokens of context, and `/turns`, the Stream tab, todo, tokens and fleet rows were all empty, because the transcript lived in the workload's home and `SessionExplorer._remote_summary` listed it off the sidecar alone (`transcript_path=None`), so `read_turns` searched the local repo root and found nothing. Rather than a second road into each reader (the per-tick parse through the worker that the tail bullet above rejected, or a daemon inside every sandbox federated back through a reverse tunnel the sandbox's deny-by-default policy forbids), the worker follows its own provider's transcript files and POSTs the appended bytes to `POST /mailboxes/transcript` (fenced exactly like `/spool`), and the daemon appends them under `paths.agent_workspace_config_dir(id)` at the same path relative to the provider's config root. **`AgentAdapter.transcript_root(path)` is the declaration that makes a tool replicable**: the files must be append-only for the host's file size to be a complete cursor, so claude_code and codex answer their root and OpenCode (one SQLite database, written in place), generic and mewbo answer `None` and keep the sidecar-only shape; the worker treats `None` as "nothing to send", never as a special case. **The worker declares `transcripts=1` plus its own `cwd` at registration** (the `live`/`reads` precedent: an older worker queues an unknown op as prompt text), and the daemon then records a `TranscriptContext(config_dir=<mirror root>, agent_cwd=<workload cwd>)` on the REMOTE record (`WorkspaceManager.record_mirrored_transcript`, inside the registration's lifecycle hold), which is the SAME namespace bridge a container's mount table answers: from that moment `transcript_scope`, `primary_transcript`, `/turns`, the activity blend, todo and the usage audit resolve the copy with no change of their own. A remote launch never passes through a `LaunchBackend` (`_launch_remote` → `RemoteRuntime.launch`), which is why the context is recorded at REGISTRATION rather than at launch: only the worker knows the cwd its provider encoded into the transcript's folder name. **The sync protocol is one answer**: a chunk is applied only at the host's current size, any other offset is 409 carrying that size, and the worker adopts it and re-reads, so a reconnect replay, a daemon restored from an older state dir, and a first chunk for a file the host already holds all correct themselves on the next POST. A separate size query and a resync-on-registration were built first and DELETED, because mutation showed them redundant with the 409 arm (the test that bit was "the host loses bytes between two connections"). Cost: O(appended bytes) per edge, no timer (a provider frame is the edge, a quiet agent sends nothing), one bounded chunk per POST (`TranscriptMirror.CHUNK_LIMIT`), and one copy on the host, which every other runtime already keeps (measured here: 1,502 transcripts, 725 over 1 MB, the largest 177 MB, which is why nothing is ever re-sent whole). Seeding a fresh workload from that copy is the next bullet; the pane is the one after.
- **A remote RESPAWN continues its session by SEEDING the new workload's home from the host mirror (#1102).** `respawn` already decided `resume` from `_pinned_session_materialized`, which since #1099 reads the MIRROR and answers True, but `_launch_remote` dropped it, so the new worker launched `--resume <id>` with `config.resume=False`, skipped `_resumable`, and asked the provider to resume a transcript its empty home did not hold. Now the answer reaches the spec, and before the provider starts the worker lists `GET /mailboxes/transcript/files` and reads `GET /mailboxes/transcript` in `CHUNK_LIMIT` pieces, writing each file at the same relative path under `AgentAdapter.transcript_home()` (where the tool WRITES; `None` exactly where `transcript_root` is). The mirror's own offsets then start at those sizes through the ordinary 409, so nothing is re-sent. A failed seed is best-effort and `_resumable` mints the pinned id fresh. These reads run before the provider starts, so before the worker can register: the fence is the bearer alone, which is no wider than `/turns`, and the routes answer only the record's own session of a REMOTE workspace. This is also the upgrade path for a workspace hibernated before a worker change: a wake restores the snapshot's OLD worker, a respawn starts the current image and keeps the conversation.
- **A remote workspace's Stream tab is its worker's own output, replicated on demand (#1101).** The tab is a host `capture-pane` and a remote workload has no host pane, so it was empty for every remote workspace. A native pane holds only what the worker prints (`emit`, and `trace` now routes through it), so the worker keeps the last `PaneLog.LIMIT` lines (500, the host's `peek_history_lines`) and posts new ones to `POST /mailboxes/pane` while WATCHED, at most once per `_PULSE_INTERVAL_SECONDS`. The watch is the existing `LiveHub` room: a pane viewer joins it like a live-step viewer, so the first viewer of either sends `watch on`, and no new op exists for an older worker to misread. The daemon's replica is the same `PaneLog` class (one numbering rule for both halves), lives only as long as the room, and `pane/stream` branches on `Runtime.REMOTE` to serve it in the host pane's frame shape, so no client changed. A batch is applied only as the replica's next lines, else 409, and the worker answers any refusal by resending its whole ring with `reset`; a new watch always starts with a reset, so a viewer never opens on a blank screen. NOT covered: output of servers the agent starts in the sandbox, which never passes through the worker (the panels feature's remote twin).
