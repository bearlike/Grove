# grove.core.agents — tool-agnostic agent introspection (AgentAdapter + ClaudeCodeAdapter)

> ↑ [grove.core](../CLAUDE.md) · [root](../../../../CLAUDE.md)

This package reads an agent tool's native sessions and normalizes them to the `AgentActivity` / `AgentSession` model (plain frozen dataclasses in `model.py`). Clients and the `ActivityService` consume only the normalized model — never a tool's raw transcript. The `AgentAdapter` Protocol is the seam; impls: `ClaudeCodeAdapter` (filesystem transcripts), `CodexAdapter` (filesystem rollout JSONL), `GenericAdapter` (no-op), and `MewboAdapter` (REST-backed, #36 — all HTTP through `grove.core.mewbo.MewboClient`, reading `GroveConfig.mewbo`: `base_url`, `api_key_env` (env-var NAME, never a secret), `timeout_seconds`). Adapters declare `remote: bool` alongside `kind` — `True` (mewbo) means the work runs on a backend and the local tmux pane says nothing about it, so the blend must not demote the adapter's reported WORKING on a quiet pane (gating on tmux read every busy remote agent as IDLE).

**The session-read surface is keyed by `(cwd, session_id)`, never by paths.** `parse_activity` / `read_turns` / `transcript_digest` take `(cwd, session_id)`; how that resolves to backing storage (a transcript glob, an HTTP call) is each adapter's internal detail — that is what lets a remote adapter fit the seam without faking filesystem `Path`s. `locate_transcripts` is the one deliberately filesystem-shaped method, kept for callers that genuinely want the files (`manager.primary_transcript`, `SessionExplorer.transcripts`, CLI dump, transcript-path display); remote adapters return `[]` there, and `SessionSummary.transcript_path` is `Optional` for the same reason.

## The provider-boundary rule

**Patch the provider boundary, never model behavior.** Grove writes code only for provider/model *parameter and protocol* differences: how an invocation is launched, how tool calls are passed, how responses (and their varied content-block types) are received, normalized, and presented — accurately, across every type exchanged. It never adds code to correct, second-guess, or work around what a model *does* — that output is non-deterministic black-box (treat it as such, per [root](../../../../CLAUDE.md)). An adapter normalizes *shape*, not *semantics*. Adding a new tool (opencode, aider, …) is one adapter module + one `registry.get_adapter` entry; clients and the `ActivityService` keep consuming only the normalized model. (`claude_code`, `codex`, `mewbo` all rode in this way — the seam held, zero client changes each time.)

## Agent questions — the structured ask-the-human contract (#74)

**One provider-neutral target, `AgentQuestion` (`model.py`), normalized at the boundary; the renderers never see a native tool shape.** `AgentQuestion.from_tool_call(name, raw_input, call_id) -> tuple[...]` is the *single* normalizer both adapters call (DRY across the provider boundary), and `QUESTION_TOOL_NAMES` / `AgentQuestion.recognizes(name)` is the *single* definition of "what is a question tool" — the Claude status path reuses it for BLOCKED, so "is this a question" can't drift between rendering and status. A question rides the transcript as `DigestEntry(role="question", question=…)` **inline in turn order** (one batch question → N entries sharing `group_id`), so both clients add one role branch and the fetch-on-demand `/turns` endpoint serializes it for free — nothing new on the hot SSE path.

- **A `tool_result` is a forward reference — resolution needs a pre-scan, never an inline lookup.** The answer (`tool_result` / Codex `function_call_output`) always lands *after* the question's tool call, possibly turns later. Both parsers build a `group_id → answer_text` map across all records/lines *first*, then stamp each question via `q.resolved(answer)` while rendering. Resolution is **group-level** (the whole batch shares one tool-call id; the result is one blob) — no semantic per-question split of the answer (that would be guessing model output).
- **Claude:** `AskUserQuestion` carries a *batch* (`input.questions[]`, mixed kinds, `multiSelect`/`options`/`header`); `ExitPlanMode` is a `confirm` (the plan is the prompt, no options). The old one-line `_tool_text` `AskUserQuestion: <first q>` render is superseded for turns; `digest()` (the LLM-interpreter seam) still emits the bare tool name — fine, it strips payloads by design.
- **Codex persists no native question** (approvals are interactive — unchanged). A question only reaches a rollout as a `function_call` whose name is a question tool (an MCP-bridged `AskUserQuestion`): `arguments` is a JSON **string** (`parsed_arguments()` json-loads it; `tool_search_call` already carries a dict and has no `call_id`, so question extraction is gated to `function_call` only). This is shape normalization for a real Codex+MCP configuration, not fabricating that Codex asks questions.

## File edits — the structured diff contract (transparent-edits epic)

**`FileEdit` (`model.py`) is the file-edit sibling of `AgentQuestion` — same shape of solution, same reason.** `FILE_EDIT_TOOL_NAMES` / `FileEdit.recognizes(name)` / `FileEdit.from_tool_call(name, raw_input) -> tuple[FileEdit, ...]` is the single normalizer every adapter calls, gated right next to the existing `AgentQuestion.recognizes` check in each adapter's per-call dispatch (`claude_code.py::turn_entries`, `codex.py::_tool_entries`, `mewbo.py::_turn_entries`). A recognized edit rides the transcript as `DigestEntry(role="file_edit", file_edit=…)` — a **new**, distinct role (not a flag on `role="tool"`), which is what keeps it out of the webapp's "Used N tools" fold for free (that grouping only merges consecutive `role=="tool"` entries) and gives it the same forward-compat story every other role already has (an old client that doesn't know `"file_edit"` degrades to a quiet note, never breaks).

- **No disk-read fallback, ever — by design, not an oversight.** `old_text` is empty whenever the tool call itself didn't carry a "before" (a full-file `Write`/`content`-shaped call). A post-hoc read can't recover the real pre-edit state anyway: by the time any parser runs (especially the fetch-on-demand `/turns` request, possibly long after the edit), the file already reflects the edit. Validated against a comparable shipped product's own transcript-diff logic, which takes the identical args-only, no-disk-read approach — an honest all-additions diff beats a fabricated or stale "before". If this ever needs revisiting (e.g. a `Write`-over-existing-file case proves annoying in practice), the only way to get a *genuine* pre-edit snapshot is real-time capture at tool-invocation time — the existing `PreToolUse` hook sidecar (see "Live question capture" below) is the seam that could carry it, Claude-only, deliberately not built.
- **`MultiEdit`-shaped batches yield N `FileEdit`s from one call**, mirroring the `AskUserQuestion` batch → N `question` entries precedent exactly (`from_tool_call` returns a tuple for the same reason).
- **A recognized-but-unparseable payload falls through to the generic tool digest, never emits an empty/broken `file_edit` entry** — same defensive posture as every other adapter parse path here (a junk block drops, never raises).
- A unified-diff-shaped **patch body** (Codex's `apply_patch`) reconstructs `old_text`/`new_text` by classifying each line (context → both sides, `-` → old only, `+` → new only), recovering the path from a `*** Update File: `/`+++ b/`/`--- a/` marker when the call didn't carry one separately — this is line-classification of a known text format, not "guessing model semantics".

## Todo lists — the structured checklist contract (#184)

**`TodoList`/`TodoItem` (`model.py`) is the THIRD structured-payload sibling of `FileEdit`/`AgentQuestion` — identical recipe.** `TODO_TOOL_NAMES` / `TodoList.recognizes(name)` / `TodoList.from_tool_call(name, raw_input) -> tuple[TodoList, ...]`, gated right after the `FileEdit` branch in every adapter's per-call dispatch (`claude_code.py::_assistant_entries`, `codex.py::_assistant_entries`, `mewbo.py::_turn_entries`), riding the transcript as `DigestEntry(role="todo", todo=…)`. Before this, `TodoWrite`/`update_plan` fell through to `role="tool"` and the whole list was discarded.

- **One tool call is ONE list**, so `from_tool_call` returns a **0-or-1-tuple** (not the batch-returns-N of the edit/question siblings) — an empty/all-unreadable list → `()` (degrade to nothing, no card), everything else → a 1-tuple. The adapters still share the one `entries.extend(...)` dispatch shape.
- **Real on-host shapes, pinned (NOT a guessed fixture):** Claude `TodoWrite` = `input.todos[]` with `content`/`status`/`activeForm`; Codex `update_plan` is a **`function_call`** whose `arguments` JSON-string carries **`plan[]` with `step`/`status`** — NO `content`, NO `activeForm` (verified against a real `~/.codex` rollout, codex 0.114). `from_tool_call` reads `todos` else `plan`, and each item's text from `content` else `step`. **Resolved caveat (#188, 2026-07-08):** an earlier session found no real `TodoWrite` tool_use on this host and guessed "the profile suppresses it" — the real reason is this host's Claude Code build has moved ON from `TodoWrite` entirely, superseded by the Task system below. The Codex side stays pinned to on-host truth as documented.
- **Status coerces to `"pending"`** for any value outside the normalized `pending`/`in_progress`/`completed` triple (both providers agree on it) — shape normalization / the safe "not started" default, never guessing model intent, never raising. `TodoList.summary` (`"<done>/<total> done · <in-progress item>"`) is the `DigestEntry.text` fallback a role-unaware consumer reads.

### The Task system — TodoWrite's Jan-2026 successor (#188)

**Anthropic replaced `TodoWrite` with a split-call "Tasks" system on builds that ship it: `TaskCreate` (one per item) + `TaskUpdate` (one per change), `TaskList`/`TaskGet` as read-only queries of the same board.** `TASK_TOOL_NAMES = {"TaskCreate", "TaskUpdate"}` is the recognizer — deliberately narrower than `TODO_TOOL_NAMES`, and NOT unioned into it, because the reconstruction shape is fundamentally different (see below). `TaskList`/`TaskGet` stay unrecognized (read-only, no new state to fold — they render as ordinary bystander tool calls). **`TaskOutput`/`TaskStop` are a DIFFERENT, unrelated concept** — background shell/agent process output + cancellation, confirmed via those tools' own on-host descriptions — never route them here even though the name family overlaps.

- **Why not a `TodoList.from_tool_call` variant:** that recipe is pure, one-call-→-one-list (a `TodoWrite` always carries the WHOLE list). Tasks split creation and mutation across separate calls correlated by a server-assigned id the call itself never carries — a `TaskCreate`'s id rides back ONLY in its own `tool_result` text (`"Task #<n> created successfully: <subject>"`, verified on-host). So materializing "the list as it stands" needs a running fold across the whole transcript, not a per-call pure function.
- **`TaskBoard` (`model.py`) is that fold** — a small mutable accumulator (`create`/`update`/`snapshot`), fed one call at a time by `claude_code.py`'s existing linear parse (`turns()` already builds a `tool_use_id → tool_result text` map for question resolution; `TaskBoard.created_task_id` reuses that SAME map, no second pre-scan). `snapshot()` returns a genuine `TodoList` — the whole point being **zero new wire contract and zero webapp changes**: every mutating call emits `DigestEntry(role="todo", todo=board.snapshot())` exactly like `TodoWrite` does, so the existing #184 pinned card renders either provider shape for free. `create`/`update` return whether they changed anything; `False` (unresolvable create id, update to an untracked id, unreadable payload) falls the call back to the generic tool entry instead of a no-op snapshot.
- **Fields this board doesn't model:** `owner`/`addBlocks`/`addBlockedBy` ride the real `TaskUpdate` wire but have no `TodoItem` equivalent and the existing card doesn't render them — dropped deliberately (YAGNI until a consumer needs them), not a parsing gap.
- **An unrecognized status on UPDATE is ignored, not coerced** — the opposite of `TodoList._item`'s CREATE-time coercion. Coercing an update's bad status to `"pending"` would silently regress an in-progress/completed task backwards on a provider quirk; ignoring it just leaves the last-known-good status standing.
- Verified end-to-end against real multi-hundred-line on-host transcripts (`~/.claude/projects/*Grove*`), including a session reconstructing a 10-task board correctly across 25 mutating calls.

## Claude transcript parsing

**Encode these hard-won facts; each is a trap if forgotten** (verified against real on-host JSONL, Claude Code 2.1.x):

- **A `type:"user"` line is usually NOT a human turn.** `tool_result` blocks carry `role:"user"` (one real session: 4683 user lines, 80 real turns). The real-turn filter is the whole game: not sidechain/meta, no `tool_result` block, text free of `<command-*>` / `<bash-*>` / `Caveat:` / compaction markers.
- **Locate transcripts by globbing the session UUID, never by decoding the project folder name.** The cwd encoding (**every non-alphanumeric char → `-`**, per the official Agent SDK sessions guide — not just `/` `.` `_`) is lossy and irreversible (anthropics/claude-code#7009). Confirm the match via each line's `cwd`.
- **Status comes from the tail assistant `stop_reason`** (`tool_use` → working, `end_turn` / `stop_sequence` → waiting; no LLM needed) — **and a trailing `tool_result` line advances the tail too** (2026-06-11): mid-tool the physical last line is a `tool_result` carrier, and without advancing on it the status reads the *previous* assistant's `stop_reason` — one whole turn of lag (a busy session reporting WAITING).
- **One JSONL line is NOT one logical record — Claude Code 2.x writes one line PER CONTENT BLOCK.** All lines of one API response share `(message.id, requestId)` with *distinct* `uuid`s and *identical* `usage`/`stop_reason` (verified on-host 2026-06-11: 123/123 multi-line messages, block order `thinking → text → tool_use*`). Two identity layers in `_read`: `uuid` = line identity (a repeated uuid is a resume/fork replaying history → drop); `dedup_key` = logical identity (a new line under a seen key is a split-block sibling → **merge its blocks** via `absorb_continuation`, count usage once). The old first-line-wins drop kept only the leading `thinking` block — every text/tool follow-up vanished from turns, digests, and tool counts while all fixture-based tests stayed green (fixtures packed blocks into one line; pin this shape against real JSONL).
- **A delivered `<task-notification>` is a plain `type:"user"` line** (no `isMeta`, no `tool_result` block) — without its marker in the non-human filter it renders as a raw-XML "user prompt" in every client. It is classified `is_task_notification` → the `notification` digest role (summary/result extracted, never raw markup) and it advances the tail to WORKING (the agent's move). The same envelope also appears in `queue-operation` / `attachment` records — those are queue plumbing, skipped; only the delivered user line counts.
- **A backgrounded `Agent`/`Task` spawn returns twice: an immediate launch-ack `tool_result`, then the real return as its task-notification.** `_SubagentFleet` closes a foreground id on `tool_result` but a background id (`input.run_in_background`) only on the notification carrying its `<tool-use-id>` — closing on the ack read every background fleet as 0. `Task` is the pre-2.1 name of the `Agent` tool; treat both.
- **An assistant tail holding an unanswered `AskUserQuestion`/`ExitPlanMode` is BLOCKED, not WORKING** — the one transcript-visible action-required signal (the answer's `tool_result` advances the tail back to WORKING). Permission prompts never reach the JSONL; they remain hook-sidecar-only.
- **`/clear` rotates the session id in-process, and a `SessionEnd` sidecar / a pane `/resume` are the same dead-pointer shape**: the minted `--session-id` becomes a dead pointer (its transcript may never exist, or its sidecar's latest event is `SessionEnd`) while the live conversation continues under a *different* id in the same cwd. Adapter-side this just means "minted id with no file is not necessarily young" and "a resumed session's transcript is born *before* the workspace"; the recovery policy (a *transcript-less* SessionEnd = dead pointer, PANE-verified sidecar-as-adoption-evidence for a resumed session, cheap-birth pre-filter) lives in [grove.core](../CLAUDE.md)'s `sessions_for` (#117; hardened by the 2026-07-05 review wave).
- `_parse_timestamp` always returns an **aware** datetime (tz-less strings assumed UTC) — downstream freshness math subtracts from `utcnow` and a naive value would raise mid-poll.
- `replies_per_turn` is the per-turn breakdown: `human_turns == len(replies_per_turn)`, `assistant_replies == sum`.
- **Defensive parsing:** per-line `try/except`, tolerate `FileNotFoundError`, and **coerce booleans that arrive as strings** (`isSidechain:"false"`) — never `bool(raw)`.
- `transcript_digest()` is the reserved seam for the future external-LLM interpreter (#20); it strips `tool_result` payloads.

## Codex transcript parsing

**Verified against real on-host rollouts (codex 0.125.0); pin against real JSONL, never a fixture — same law as Claude.** `codex.py` mirrors the Claude decomposition exactly: `_CodexHome` (paths) / `_RolloutLine` (one line) / `_RolloutParser` (aggregate) / `CodexAdapter`. Each fact below is a trap if forgotten:

- **Path is date-partitioned, NOT cwd-encoded** (the opposite of Claude): `$CODEX_HOME`-or-`~/.codex` / `sessions/YYYY/MM/DD/rollout-<ts>-<uuid>.jsonl`. Session id = the `uuid` (= `session_meta.payload.id`); locate globs the uuid suffix and confirms via the in-file id, never a folder name.
- **cwd lives ONLY in `session_meta` (line 1) and `turn_context`, not on every line.** The Claude reflex of reading any line's `cwd` returns nothing. Discovery reads a bounded head (≤8 lines) for `session_meta` cwd; that one head read backs both `discover` and `list_sessions`.
- **Codex DUAL-RECORDS — the central trap (its analogue of Claude's split-block dedup).** Every message is written twice: as a `response_item` (structured transcript) AND as an `event_msg` (`agent_message`/`user_message` mirror). The rule, enforced in `_RolloutLine` classification: **conversation/turns/replies/tools ← `response_item` ONLY; status/tokens ← `event_msg` ONLY.** Counting from both doubles every message — green against packed fixtures, wrong against real files.
- **Status from explicit turn boundaries, not a stop_reason.** `event_msg/task_started` + `task_complete` share a `turn_id`; an unmatched `task_started` → WORKING, all matched → WAITING (`_EventState.state`). Fallback with no task events: trailing assistant `message` → WAITING, trailing human/tool → WORKING. No transcript-visible BLOCKED — Codex approval prompts are interactive, never persisted (same as Claude permission prompts being hook-only).
- **`token_count.info.total_token_usage` is CUMULATIVE** (`input_tokens` strictly grows): take the LAST populated report, never sum (summing running totals multiplies). `info` is `null` early in a session, so tokens legitimately read 0 until the first usage report.
- **`launch_decoration` is empty — Codex cannot be launched with a chosen id** (thread id is internal `Uuid::new_v4`; `--session-id` is resume-only). So `_mint_agent_session_id` returns `None` and every Codex session reaches Grove through `discover_sessions` like a hand-started Claude run — the discovery + `sessions_for` primary-adoption path in [grove.core](../CLAUDE.md) already covers it, **zero new engine wiring**.
- **Reasoning is a black box:** `response_item/reasoning` is almost always opaque `encrypted_content` with empty `summary`. Surface a marker only when `summary` carries readable `summary_text`; never read/decrypt `encrypted_content` (normalize shape, not semantics).
- **Real human turn = `response_item message role:"user"` minus the injected preamble** (text holding `<environment_context>` / `<user_instructions>` / `# AGENTS.md` / `<permissions instructions>`); `developer`-role messages are system injections, never turns. The "a user line isn't a human turn" trap again — different markers.
- **`session_meta.payload.git` carries `{branch, commit_hash, repository_url}`** when the cwd is a repo — the `git_branch` source (SDK-parity), the only record that has it.
- **`apply_patch` is a `custom_tool_call`, NOT a `function_call`** (verified on-host, codex 0.125.0, 2026-07-08: `payload == {"type":"custom_tool_call","call_id":…,"name":"apply_patch","input":"*** Begin Patch\n…\n*** End Patch"}`). `input` is the raw patch body — a plain string, unlike `function_call.arguments` which is JSON. Before this was discovered, `custom_tool_call` wasn't in `is_tool_call`'s payload-type set at all, so **every `apply_patch` edit was invisible** — uncounted, absent from turns/digest, silently skipped. `is_tool_call` now includes it; `is_custom_tool_call` + `custom_tool_input()` are its accessors, mirroring `is_function_call`/`parsed_arguments()`'s style. Any *other* future Codex custom tool rides the same widened classification and renders as a generic tool entry unless it also matches `FileEdit.recognizes`.

## Deterministic session correlation

**Grove mints the session id and launches with it; it never scans to guess.** `WorkspaceManager.create()` mints a canonical dashed UUID (Claude requires RFC-4122, distinct from the bare-hex workspace id), asks the adapter for a `launch_decoration` (`["--session-id", uuid]` for Claude Code, `[]` for generic/shell), threads it through `tmux.build_workspace_layout` (shell-quoted), and persists `WorkspaceState.agent_session_id`. So the transcript path is known by construction.

- **The `--session-id` is never hard-coded in `tmux.py`** — it comes from the adapter. `AgentSpec.kind: Literal["claude_code","generic","mewbo"]` selects the adapter (built-in `claude` ships `claude_code`).
- **resume keeps the persisted id (continue); respawn mints a fresh id (new session).** That fork lives in exactly one helper (`_mint_agent_session_id` in `manager.py`, with `_compose_launch` composing the argv) so the verbs can't drift. The same helper holds the minting asymmetry: claude_code ids are client-minted, mewbo ids are server-minted (see [grove.core](../CLAUDE.md)).
- **Each adapter declares a `resumable` class attribute; `_RESUMABLE_KINDS` DERIVES from it.** `resumable = True` (claude_code, codex) means `launch_decoration(..., resume=True)` yields a real handle; the manager builds `_RESUMABLE_KINDS = {a.kind for a in all_adapters() if a.resumable}` rather than hand-listing, so a future resumable adapter can't be missed by a stale constant. Add a new resumable tool → set `resumable = True` on its adapter and the create/resume gates pick it up for free.
- **`launch_decoration(session_id, *, resume=False)` is the mint-vs-resume seam (#120).** The manager gates resume to `_RESUMABLE_KINDS` (`claude_code`, `codex`) *before* calling, so per-adapter it's a pure two-form switch: claude_code `--session-id <id>` → `--resume <id>` (plain `--resume` KEEPS the same session id/file — it does not rotate the id, that needs `--fork-session` — so pinning `agent_session_id` to the resumed id is correct); codex `[]` → `["resume", <id>]`. **The codex resume subcommand rides *after* the configured command with no injection machinery** because codex's grammar is `codex [OPTIONS] <COMMAND> [ARGS]` — top-level flags precede the subcommand, so `codex --full-auto` + `resume <id>` = `codex --full-auto resume <id>` parses correctly (verified against codex-cli 0.125.0; `resume` also accepts `-m/--model`, so the appended `--model` still lands). On a codex resume the chosen uuid is persisted as `agent_session_id` — even though codex normally mints nothing and relies on fs discovery, an explicit resume is tracked by construction.
- **The CLI-vs-Agent-SDK resume cwd trap** (matters only if an adapter ever swaps its launch mechanism): the `claude` **CLI** `--resume <id>` is worktree-aware — it resumes a session recorded in the same *repo* even from a different worktree dir (claude ≥2.1.198). The **Agent SDK**'s resume is strictly cwd-keyed (it decodes the encoded-cwd projects folder), so a resume launched from a different dir than the session was born in would miss. Grove launches the CLI, so worktree placement is fine today; anyone porting a resume path onto the SDK must anchor the cwd to the session's original.
- **Per-create model selection rides the launch via `adapter.model_decoration(model)` (#96)** — a second decoration seam alongside `launch_decoration`, for the same reason: the *flag* is provider-specific. `claude_code` / `codex` → `["--model", <id>]`; `mewbo` / `generic` → `[]` (no launch model flag — the model is server-side or absent). **mewbo's model is still honored (#98):** with no CLI flag, the per-create model is forwarded at REST session-create instead — `_mint_agent_session_id(..., model=request.model)` → `MewboClient.create_session(model=...)` adds it to the `POST /api/sessions` body (best-effort: an extra body key is harmless if the server ignores it). So `model_decoration` staying `[]` for mewbo is correct — the forward happens on the create path, not the launch path; `generic` truly has no model. `_compose_launch` appends it **independently of the session id** (codex mints none but still honors `--model`) and **before** the trailing `initial_prompt` positional. The value is forwarded verbatim — the provider boundary: Grove never validates or interprets a model id, the tool does. The wire field is `CreateWorkspaceRequest.model`, create-only like `initial_prompt`/`skip_init` (never persisted, never re-applied on resume/respawn).
- `manager.primary_transcript(id)` resolves the file(s) via the adapter, returning a `tuple` (snapshot convention; also dodges the `list`-method-shadows-`list[]`-builtin mypy trap inside `WorkspaceManager`).
- **The create-time `initial_prompt` (#48) rides the LAUNCH, never post-boot pane typing.** claude_code appends it as a trailing POSITIONAL on the launch argv (`claude … "<prompt>"` boots already working on it), shell-quoted through the one `tmux.build_workspace_layout` path — typing into the pane after boot races the agent (the documented swallowed-Enter trap). A remote adapter (mewbo) has an empty `launch_decoration`, so its prompt re-engages through the existing `/message` dispatch (`_deliver_remote_initial_prompt` → `_steer_remote`) after the workspace is persisted — best-effort, a delivery failure never rolls back the created workspace. generic/shell has no prompt concept and drops it. Composition stays in `manager._compose_launch(initial_prompt=…)`, gated to CREATE only (never resume/respawn, like `skip_init`).

## Model catalog & discovery — the ≤10 picker seam (`available_models` / `resolve_models`)

**`adapter.available_models(command) -> tuple[str, ...]` is the discovery SIBLING of `model_decoration`, under the same provider boundary: it OFFERS a model list for a create-form picker, never a validated allowlist.** Create still forwards any id verbatim, so a model absent from the catalog works fine — the catalog only informs the human/agent choosing. Each adapter answers per its provider's real capability, and `command` (the configured `AgentSpec.command`) supplies the binary — no tool name is hard-coded:

- **`codex` — the real auto-refresh.** Reads `codex debug models` (structured JSON `{"models":[{slug, visibility, priority, …}]}`), keeps `visibility == "list"` (drops internal `"hide"` rows like `codex-auto-review`), orders by the catalog's own `priority` (0 first), returns each `slug`. Verified codex-cli 0.125.0. **Trap: the output is ~190 KB** because every model embeds a giant `base_instructions` prompt — parse ONLY `slug`/`visibility`/`priority`, never keep `base_instructions`. The one subprocess in the adapter, split into two seams: `_probe_codex_models(binary) -> str | None` (best-effort — `shell=False`, fixed list argv, bounded `_MODELS_PROBE_TIMEOUT`, `None` on any OSError/nonzero/timeout, never raises) and the pure `_parse_codex_models(raw)` (unit-testable without a subprocess). `_probe_codex_models` is the seam `tests/conftest.py::_offline_codex_models` autouse-patches (release-checker precedent) so the suite never shells out.
- **`claude_code` — aliases, because there is NO CLI enumeration.** `claude` exposes models only through the interactive `/model` picker; `claude --help`/`--list-models` list nothing (confirmed via DeepWiki + on-host). Its tier aliases `("sonnet","opus","haiku")` ARE the stable public `--model` vocabulary — each re-points to the current model of that tier every release (a new Opus keeps `opus`), so offering them never goes stale the way a dated id would. This is a mechanism default, NOT a hard-coded dated id; full ids / gateway models still work (forwarded verbatim), and `AgentSpec.models` overrides.
- **`mewbo` / `generic` — `()`.** No local CLI catalog to read (mewbo's roster is server-side; a shell has no model). A deployment pins its offered ids via `AgentSpec.models`, which the resolver prefers.

**`registry.resolve_models(*, kind, command, configured)` is the SINGLE composer — the one place the catalog is built, so every surface shows the same list.** `configured` (`AgentSpec.models`) wins WHOLESALE when non-empty (a pin/curate/reorder seam, mechanism not policy), else falls through to `available_models`; then de-dup (order-preserving, drop empties) and cap at `MODEL_CATALOG_CAP = 10` (the "≤10" rule — display only, never restricts create). One source, many renderers: the daemon `GET /agents` route resolves it into `AgentSummaryView.models` (in the executor — codex discovery is a subprocess), and the webapp picker, `GroveClient.list_agents` → the MCP `grove_list_agents` tool, the TUI create screen (in-process), and `grove create --model` all read that one catalog. `MCP/CLI` never import adapters — they get the resolved list over the wire via `AgentSummaryView`.

## Mewbo — the remote adapter (#36)

**Pure logic over `MewboClient` payloads; all HTTP stays in `grove.core.mewbo`.** Wire facts verified against the Mewbo console client + API guide (2026-06-11):

- **Lazy cached client.** Adapters are registry singletons, but this one needs config + an HTTP pool: built on first introspection call from the ONE global config (`load_config(repo_root=None)` — the ActivityService rule), cached on the instance; `MewboAdapter(client=...)` is the test DI seam (`httpx.MockTransport`, no monkey-patching). Importing the registry never reads config or opens sockets.
- **`GET /events` is authoritative** — top-level `status` / `done_reason` / `title` come from the server's `summarize_session`; never reconstruct state from the timeline tail. Events are `{ts, type, payload}` rows. Status map: `running`→WORKING; settled (`completed`/`done`/`finished`/`interrupted`/`idle`/`waiting`)→WAITING; `waiting_user`/`needs_input`/`blocked`→BLOCKED; `failed`/`error`→ERROR; unrecognized/missing→UNKNOWN. An error-ish `done_reason` promotes any terminal status to ERROR.
- **Peak vs billed tokens — never mix (Mewbo #45).** `GET /agents` `total_input_tokens` is PEAK semantics (root peak + per-sub-agent peaks, the context-pressure number); the cumulative billed sum is the separate `total_input_tokens_billed` on `/usage`. `tokens_in` uses the peak; the no-`/agents` fallback mirrors it (max of `llm_call_end` `input_tokens`, sum of `output_tokens`).
- **Mewbo `user` events ARE real human turns** (unlike Claude transcripts) — turn buckets split on them; `agent_message` + `completion` are the assistant replies. Tool events carry `tool_id`/`operation`/`tool_input`; result events carry `tool_id` too, so count only the call side (`"result" not in payload`) or every step doubles. `action_plan` steps are `{title, description}`.
- **Rendered turns surface call AND result detail, but counting stays call-side.** `read_turns`/`digest` emit the `tool_input` summary on the call entry (dict → `k=v` pairs, bare string passthrough — `tool_input` is polymorphic per tool) and a *separate* `tool` entry for the result (`error` preferred over `result`), plus `action_plan` step descriptions — Claude-adapter render parity. `is_tool_result` (`"result" in payload`) is the exact mirror of `is_tool_call`, so the result twin is rendered but never counted: richer rendering never moves metrics/tokens/status. Everything comes from `GET /events` already fetched — no new endpoint. Turns carry full text (`_TURN_TEXT_CAP`), digest re-truncates (`_DIGEST_TEXT_CAP`) — the same split Claude draws.
- **The tool NAME for `FileEdit`/recognition purposes is `operation`, not `tool_id`.** `tool_id` is a per-step identifier (reused across the call+result pair); `operation` is the underlying tool's name (e.g. `"Edit"`), read via a small `operation` property mirroring `tool_id`'s own narrowing. `tool_label()` (`f"{tool_id}: {operation}"`) is a *display* string, never a recognition key — don't recognize off it.
- **No local surfaces by design:** `launch_decoration`/`locate_transcripts`/`discover_sessions` return empty — no CLI to decorate (the tmux agent window runs whatever the AgentSpec names, typically a shell), no transcript files, and a remote session can't be "hand-started in a cwd" invisibly to Grove. `list_sessions(cwd)` filters `GET /api/sessions` rows by `context.cwd` (persisted by the #91 cwd anchoring) and skips rows without one — honest filtering; minted-id association lives in `SessionExplorer`.

## Push status — hook sidecar (#18)

**A per-session sidecar that a Grove-managed Claude Code hook writes; it overrides the polled blend, and installs without touching the user's settings.** Polling (`stop_reason` + tmux) can't separate waiting-from-done and is blind to a permission prompt; hooks push exact lifecycle events.

- `hook.py::ClaudeHook` maps each event name to an `AgentActivityState`: `Notification` → BLOCKED (the signal polling can't see), `Stop` → WAITING, `SessionStart` / tool events → WORKING, `SubagentStop` → None (a finishing sub-agent never flips the main thread). It writes `<state-dir>/agent-sidecars/<session_id>.json`.
- The hidden `grove agent-hook` CLI reads hook JSON on stdin (+ `$TMUX_PANE`) and writes the sidecar — **always exits 0** (a hook must never fail the agent).
- **Sidecar staleness is transcript-supersession, not wall-clock age** (`HookRecord.supersedes_poll`, 2026-06-11). A push describes one moment; it loses the instant the transcript outruns it (`transcript.last_event_at > record.ts` — the steer-after-Stop case, where age-only trust pinned WAITING on a re-engaged agent for 5 min). Only WORKING also ages out (`DEFAULT_SIDECAR_MAX_AGE_SECONDS`, 300s — the dead-agent guard); settled states (WAITING/BLOCKED/IDLE) never expire — nothing happened since, so they're still true, and expiring BLOCKED into a polled guess re-creates the invisible-permission-prompt bug the hook exists to fix. `ClaudeHook.read` is mechanism only (read + parse); the supersession judgment needs the transcript's clock, which only the blend site has.
- **Install is additive and non-clobbering.** `cfg.hooks.enabled` makes the manager write a Grove-owned hook-only settings file and append `--settings <that file>` to the claude launch. The user's `.claude/settings.json` is never edited; uninstall is flipping the flag back. No hook installed ⇒ no sidecar ⇒ polled status stands unchanged.

## Live question capture + answering — the same sidecar carries the ask (#109)

**Claude Code flushes NOTHING to the transcript while an `AskUserQuestion` (or `ExitPlanMode`) is on screen** — the assistant message holding the `tool_use` block is written only *after* the human answers or Esc-cancels. So the BLOCKED-tail logic above (which needs the unanswered tool_use in the JSONL) can't see a *pending* question, and neither can any transcript reader. The ask-time `PreToolUse` hook is the **only** signal, verified on-host (CC 2.1.x). This is why capture rides the hook, not the transcript.

- **Capture keys off `QUESTION_TOOL_NAMES`, never a hard-coded name**, and stores the raw `tool_name` + `tool_input` (+ `tool_use_id`, `asked_at`) on the same sidecar the status push uses (`HookRecord.question`). It is normalized to `AgentQuestion` lazily via the shared `from_tool_call` seam — no second question shape. One file already read per poll now carries both live status and the live question.
- **The pending question is a tiny state machine over that one file, and its clear rules differ from the state map's** (`ClaudeHook._pending_question`): a question-tool `PreToolUse` *captures*; any other `PreToolUse` or a `_QUESTION_CLEAR_EVENTS` event (`PostToolUse`=answered, `Stop`=Esc-cancel/turn-end, `UserPromptSubmit`, `SessionEnd`) *clears*; **`Notification` and `SessionStart` CARRY FORWARD** (read-modify-write the prior sidecar). The carry-forward is load-bearing: the permission `Notification` fires ~6 s *after* the ask while the question is still up, so treating it like every other event would erase a standing question after 6 s. (`Notification`→BLOCKED is unchanged; only the question half carries.)
- **Two independent resolution signals, because hooks can be missed.** The sidecar lifecycle clears on the answer's events, AND `activity.py` cross-checks the transcript: once the tool_use + its resolving `tool_result` flush together (they only appear post-answer/cancel, `is_error` included), the group is present in `read_turns` → not pending. The cross-check is gated on `transcript.last_event_at > asked_at` so it only re-parses once the transcript has actually moved (while genuinely pending, nothing flushes, so it's free). Surfaced on the live stream as `AgentActivity.questions` — the **whole batch** (additive `AgentActivityView.questions: list`, ordered as asked; one AskUserQuestion carries up to four questions answered atomically with one POST), added to the poll fingerprint so appear/resolve streams at once.
- **Answering drives the TUI by keystroke — the one place a select-question needs more than `send_text`.** `tmux.send_keys` is the narrow primitive (a `SendKey` named-key ∈ {Tab,Enter,Escape} or a literal `-l --` text run; a StrEnum IS a str, so the dispatch checks `SendKey` first). `ClaudeCodeAdapter.build_answer_keys` is the pure, verified grammar: single-select→digit `i+1`; free-text (single-select only)→digit `len+1`+text+Enter; multiSelect→a digit per choice then Tab; a final Enter iff a review step exists (>1 question OR any multiSelect). It **branches on the normalized `kind`, not the tool name** (provider boundary), and *rejects* what wasn't verified (`confirm`/optionless `free_text`, multiSelect+text) rather than guessing keystrokes — the manager maps that `ValueError` to 422. Grammar lives entirely in the adapter; the manager only matches the captured `tool_use_id` (409 if stale/absent, re-checked right before the send) and sends. **Dispatch semantics, like steering**: 204/keys-sent is not confirmed-answered — the residual terminal race (human answers between check and send) leaves the extra keys as harmless literal text in the reset composer; resolution arrives later on the stream.

## Session exploration (list / turns / dump — issue #26)

**The adapter's read surface mirrors the official Agent SDK, without taking the dependency.** The SDK's `list_sessions()` / `get_session_messages()` / `get_session_info()` read `projects/` JSONL directly from disk (no CLI invocation) — validating Grove's approach. `SessionSummary` deliberately mirrors `SDKSessionInfo` field names (`first_prompt`, `git_branch`, `cwd`, `created_at`); we keep our own reader because it already handles what the SDK doesn't (multi-config-dir cascade, string-boolean coercion, preamble cwd scan).

- **`discover_paths` is the one scan; `discover` (ids), `discover_births` (id + BIRTH), and `list_sessions` (summaries) are projections of it.** Don't add a third scan variant — extend the tuple (it now carries `(id, path, mtime, birth)`). `discover_births` is the dashboard's **cheap adoption pre-filter**: `birth` (the first timestamped record) rides out of the SAME bounded head read that already confirms the cwd (`_head_cwd_and_birth` for Claude, `_meta_and_birth` for Codex) — never a full transcript parse — so the adoption gate rejects a historical transcript on cheap metadata and pays a full parse only for candidates that pass (per-tick cost O(new sessions), not O(history)). Returns `(id, birth, mtime)` newest-first by mtime; `[]` for generic/remote.
- **`list_sessions` builds each summary + its point-in-time `AgentActivity` from ONE parse of the main transcript** (sub-agent files are sidechain detail, excluded from summary scope). The old "full parse per tick is fine; revisit only if it measurably lags" deferral came due 2026-07-11 — it pegged the daemon on a multi-GB transcript tree; every full-file read now flows through the incremental transcript cache (section below).
- **`last-prompt` records come in two shapes** (verified on-host): with `lastPrompt` text, and leafUuid-only pointers. `last_prompt_text()` skips the pointer form — treating it as an empty prompt loses the real one.
- **`read_turns` groups assistant entries (text + tool calls, in block order) under each human turn.** Assistant records preceding any human turn (resumed/compacted head) collect under a leading turn with empty `user_text` — never dropped.
- **Watch-item: forked sessions now store a parent *pointer* and hydrate on read** (upstream changelog; the SDK rebuilds chains via `parentUuid`). No pointer records observed on-host yet — if fork-heavy transcripts start showing truncated history, this is why.
- Sub-agent files carry a sibling `agent-*.meta.json` (`agentType`, `description`) — available, deliberately unused so far (YAGNI).
- Cross-worktree aggregation (which dirs to scan, workspace/provenance annotation) is NOT adapter business — it lives in `core/sessions.py` (`SessionExplorer`, see [grove.core](../CLAUDE.md)). Adapters only ever answer for one `cwd`.

## Incremental transcript cache (`transcript_cache.py`, daemon-CPU fix 2026-07-11)

**Every full-file transcript read in both filesystem adapters flows through one mechanism: `TranscriptCache` (per path-tuple fold state, advanced by parsing only bytes appended since the last read) + `ResultMemo` (a stat-signature memo over the derived products — activity/messages/turns/digest/summary).** Why: the 2 s activity poll re-parsed every session's full JSONL (twice per workspace — `parse_activity` AND the #173 `fleet_activity → read_messages` path), and every `/activity` snapshot request repeated the scan; py-spy showed ~95 % of daemon samples in `json.loads`, two pegged executor threads, RSS ballooning past 1 GB on a ~2 GB transcript tree. Transcripts are append-only in the steady state, so an unchanged file now costs one `stat` and an active one costs only its delta. Each fact below is a trap if forgotten:

- **The fold policy is the adapter's, injected as a `RecordFolder`** — Claude's `_RecordFolder` carries the uuid-replay drop + split-block `absorb_continuation` merge (moved verbatim from the old `_read` loop); Codex's `_LineFolder` is a plain appender. The cache owns cursors, resets, byte budget, and thread-safety; it knows nothing about providers (mechanism, not policy).
- **`absorb_continuation` mutates the kept record's raw dict, so parsed dicts must be PRIVATE to one fold state.** Never share raw lines across fold states or refold previously-folded objects — a second absorb of the same sibling duplicates content blocks silently. A state reset therefore always re-parses from disk, never from cached objects; that is why there is no shared per-file line cache underneath.
- **Reset (full re-read) triggers on: inode change, any non-growth size change, or a vanished file that had content.** The cursor only ever advances past the last `\n`, so a writer-in-progress partial trailing line is deferred, not skipped (UTF-8 can't straddle that boundary — `\n` is a single byte).
- **Memo values must be immutable** (frozen dataclasses / tuples — all the read products already are); they are shared across the poll thread and request executor threads. The memo key carries the method + cwd + session id (+ `last` for turns); the stat signature covers the path *set*, so a transcript appearing or a new sub-agent file invalidates naturally.
- **Both caches are module-level singletons** (they must outlive the throwaway adapter instances). Tests reset them via the adapters' public `clear_caches()` in the autouse `_fresh_transcript_caches` conftest fixture — never by patching privates. Within one test, beware same-size same-mtime_ns rewrites: the cache honestly can't see them (real transcripts only append).
- **Sort-order nuance:** `_read` still sorts per call; a record's tiebreak `index` now reflects *fold* order, not whole-file parse order, after incremental appends — only observable for no-timestamp records, which live in the file preamble and fold first anyway.

## Out-of-band discovery mechanics

**`discover_sessions(cwd, exclude_id)` finds sessions Grove didn't mint** (an agent that wasn't `claude_code` at create, a pre-minting record, or a purely hand-started `claude`). It is a read-only fs glob, so it **always runs** — adapter-gated only (generic/shell ⇒ `[]`, no-op), NOT gated by `cfg.hooks.enabled`; `hooks.enabled` gates only the push-sidecar install. **The augmentation of an already-minted session with concurrent hand-started ones is ungated too (#119, 2026-07-05)** — the old `if cfg.hooks.enabled` around that discovery blinded a hooks-off dashboard to hand-started sessions for no reason (read-only discovery needs no opt-in, exactly like the null-id path). The service calls it (and its cheap `discover_births` projection) once per cwd in the workspace's **`scan_cwds` union** (`agent_cwd` + worktree root), merging newest-first by mtime — a session hand-started at the worktree ROOT of a nested project records its cwd there, not at `agent_cwd`. The adapters still exact-match the transcript's recorded cwd (#118); the union just widens *which* cwds are scanned. The recovery *policy* that adopts a discovered session lives in [grove.core](../CLAUDE.md)'s `sessions_for` — it must NOT early-return on a falsy id.

- **`discover_sessions` returns ids NEWEST-FIRST by transcript mtime, not alphabetical.** Old behavior was `sorted()` — an arbitrary, often-dead pick. The `[:1]` rescue depends on newest-first to land the live session.
- **`_first_cwd` scans PAST the cwd-less preamble** (`mode` / `file-history-snapshot` / `summary` lines) to the first record carrying a `cwd`. Real transcripts open with two-or-three preamble lines before the cwd appears; keying off line 0 alone returns `None` and rejects **every** real transcript. Test fixtures hid this by putting `cwd` on line 0 — **verify discovery against a real on-host transcript, never a hand-built one.**
- **Config-dir cascade:** `CLAUDE_CONFIG_DIR` (CSV) → `~/.config/claude` → `~/.claude`. `projects_dirs` always also appends the latter two.

**Two operational corollaries** that bite even with the code correct:

1. **A custom-named Claude agent MUST declare `kind: "claude_code"`.** Merge-by-name doesn't inherit the built-in `claude`'s kind, so a custom-named entry like `"Claude Code (Custom)"` defaults to `generic`, mints no id, and relies entirely on discovery.
2. **Pin/neutralize a profile with `agents[].env` / `agents[].env_unset`, never the daemon's own env (#82).** A pane inherits the tmux server env (which inherited the daemon's), so a `CLAUDE_CONFIG_DIR` on the *daemon* leaked daemon → server → pane → agent — overriding the selected profile and skewing the scan. The launch boundary clears whatever `env_unset` names and exports whatever `env` names (unset-before-export, so export wins for a key in both) — **no var name is hard-coded in Grove**: to use the tool's default profile against a leaking daemon, add `"env_unset": ["CLAUDE_CONFIG_DIR"]` to that agent; to pin a specific one, set `env["CLAUDE_CONFIG_DIR"]`. The read side needs no per-agent config: `projects_dirs` already unions the default dir in, so a hermetic default-profile session is found even when the daemon's ambient value is stale.

## Native instrumentation & control — provider research facts (epic #170, verified 2026-07-08)

> Distilled from official docs + DeepWiki (`anthropics/claude-code`, `claude-agent-sdk-python`, `openai/codex`, `langfuse/*`). These facts anchor the #170 tiers — re-verify only on a major tool release, never re-research from scratch.

- **Claude's JSONL transcript is an UNVERSIONED internal format** (Anthropic: direct parsers "can break on any release"). Keep file-parsing best-effort and pinned to real on-host JSONL; the durable feeds are stream-json, hooks, and OTel.
- **Native keep-alive + input:** `claude -p --input-format stream-json --output-format stream-json --verbose` with stdin held open accepts NDJSON user turns across turns — the native replacement for pane typing. `assistant` events carry per-turn `usage` (input/output/cache_creation/cache_read); the terminal `result` carries `total_cost_usd`/`duration_ms`/per-model breakdown; `--include-partial-messages` adds live token deltas. **TTFT is NOT in stream-json** — only the beta OTel `llm_request` span carries `ttft_ms` (`CLAUDE_CODE_ENHANCED_TELEMETRY_BETA=1` + `OTEL_TRACES_EXPORTER=otlp`).
- **A pending question NEVER reaches the transcript** — Claude flushes nothing while an `AskUserQuestion`/`ExitPlanMode` is on screen (the `tool_use` lands only after answer/cancel), so transcript readers are structurally blind to it; ask-time hooks are the only signal (this is why #109 exists and why #171 makes hooks default-on). Same blindness applies to live token flow: nothing is written mid-generation — live counters come only from partial-message deltas, OTel metrics, or the wire (#177).
- **Sub-agents — two linkage layers, don't conflate (verified on-host, CC 2.1.x):** on DISK, sub-agent transcripts are separate files at `{sessionId}/subagents/agent-{agentId}.jsonl` (records marked `isSidechain: true`), threaded by `parentUuid` with `sourceToolAssistantUUID` pointing at the spawning `tool_use` assistant message; on the live STREAM, every sub-agent message carries `parent_tool_use_id` (= the spawning `Agent`/`Task` tool_use id; nesting ~5 deep). Sidecar `{transcript}.meta.json` = `{agentType, worktreePath?, description?}` (fire-and-forget — may be missing, degrade); agent name/color ride the MAIN transcript as `agent-name`/`agent-color` entries. Lifecycle edges via `SubagentStart`/`SubagentStop` hooks (`agent_type`, `agent_id`). The CLI's own sub-agent navigator is backed by exactly this lineage — reconstruct from it, nothing else exists.
- **Permission/question interception, headless-answerable:** precedence hooks → deny → ask → permission mode → allow → SDK `can_use_tool`. `--permission-prompt-tool <mcp_tool>` answers prompts with allow/deny JSON; `PreToolUse` can emit `permissionDecision` AND rewrite tool input (`hookSpecificOutput.updatedInput`); "agent needs input" = the `Notification` hook (`idle_prompt`/`agent_needs_input`/`permission_prompt` matchers). Hooks support **`"type":"http"` with a `headers` map** (Claude POSTs the event JSON, reads the decision JSON from the 2xx body; default timeout 600s — a blocking `Stop` hook is a potential long-poll delivery slot), so an http hook CAN carry the daemon bearer — #171 picks dual command+http handlers vs agent-hook-POSTs at implementation. Model-facing injection rides `hookSpecificOutput.additionalContext` (`UserPromptSubmit`/`PreToolUse`/`PostToolUse` are the unambiguous seams; `Stop`+`decision:"block"`+additionalContext is documented to continue the turn but MUST be empirically verified per #171 before building on it — `reason` goes to the USER, never the model). All hook output caps at 10k chars.
- **Mid-session controls:** the stream-json `system/init` event enumerates `slash_commands`/`tools`/`mcp_servers`/`plugins`/`model`; `/skill-name` and `/config key=value` work headless (≥2.1.181); a mid-run model switch needs the SDK control channel (source-verified `control_request` subtypes: `initialize`, `interrupt`, `set_permission_mode`, `set_model`, `rewind_files`, `mcp_reconnect`, `mcp_toggle`; CLI→SDK callbacks: `can_use_tool`, `hook_callback`, `mcp_message`; the SDK drives the CLI with `--input-format stream-json --output-format stream-json`, no `-p`). Interactive-only residue: `/login`, the `/resume` picker, Ctrl+O — presentation affordances; **auth is the only irreducible interactive need**. The Agent SDK subprocesses the same `claude` binary (SubprocessCLITransport) — capability-identical to stream-json; SDK framing is API-key auth, driving the CLI inherits the user's login.
- **Codex analogs (the seam holds):** headless = `codex exec --json` (thread→turn→item NDJSON; `turn.completed` carries usage incl. cached/reasoning; event names drift across versions — pin against the installed CLI). Rollout cwd lives only in `session_meta`. Sub-agents are real forked threads (`Collab*` events, FullHistory/LastNTurns inheritance). Network-off = `--sandbox workspace-write` + `sandbox_workspace_write.network_access=false` (default off; Claude has NO sandbox flag — tools-off = `--disallowedTools WebFetch,WebSearch`, the #148 asymmetry). Live steering = app-server JSON-RPC `turn/steer`/`turn/interrupt` (no bare-CLI Claude equivalent). **Codex ships native OTel** (`codex-otel`: per-turn tokens, `ttft.duration_ms`, OTLP http/grpc).
- **Wire-truth seam (#177):** Claude honors `ANTHROPIC_BASE_URL` (documented LLM-gateway support); Codex has `model_providers.<name>.base_url` + `env_key` — both reachable through the existing `agents[].env`/config launch boundary, so a Grove passthrough proxy needs zero tool-side cooperation and sees true TTFT + live token flow.
- **LangFuse ingestion (#175/#177):** OTLP at `{host}/api/public/otel/v1/traces`, HTTP Basic `b64(public:secret)`. Build spans with the **raw opentelemetry-sdk** — the LangFuse Python SDK's `start_observation()` has no `start_time` param (fatal for historical replay). LangFuse adopts incoming W3C trace/span ids verbatim and de-dupes → deterministic ids derived from session/turn/tool-call ids give idempotent re-ingestion. Push `langfuse.observation.usage_details`/`cost_details` explicitly (its price table can't see cache/reasoning pricing); TTFT = `langfuse.observation.completion_start_time`; observation types `agent`/`tool`/`generation` map the fleet tree 1:1.
- **There is NO uninvited input channel into a RUNNING interactive TUI session** (verified CC 2.1.x: no IPC/control socket, no queue file/FIFO — interactive input is consumed exclusively from pty raw-mode stdin; no local attach to a running session exists, the SDK spawns and owns its own subprocess). Native channels exist only when **composed at launch**: **Channels** (stdio MCP channel subprocess via `--channels` — delivers messages a running INTERACTIVE session acts on, plus a permission relay; Anthropic-auth-gated, research preview → #182), stream-json stdin / the SDK control protocol (headless), and hook injection (#171). **Send-keys Enter-swallow root cause (on-host):** bracketed paste — a `\r` landing inside the paste-accumulation window is a literal newline, never a submit; only a lone `return` keypress submits ⇒ send text and Enter as separate writes with the Enter delayed past the window (#180). **The bridge is session mobility:** conversation state lives in the session file, not the process — stop the TUI and `claude -p --resume <id> --input-format stream-json` continues the SAME session on a native channel (and vice versa back to `claude --resume` interactive).
- **The one-mechanism principle (epic #170):** the portable control/observation plane is the *native session protocol* — stream-json turns over the process's stdio + hook events + OTel/proxy spans over HTTP — which is location-independent; only the *transport* varies (local pipe / `docker exec -i` stdio / a thin shim exposing stdio over HTTP for remote runtimes). This is the Agent SDK's own architecture (a transport under a typed protocol), and Grove's `mewbo` adapter is the in-repo proof of consuming a remote session over REST. tmux is a *process plane + presentation mode*, never the control plane.

## The agentic-loop spine (`model.py`, #179) — one parse, many projections

**`AgentMessage`/`ContentBlock`/`TokenUsage` (frozen slotted dataclasses in `model.py`) are the lineage-preserving event layer the render digest is now DERIVED from — never a second parser.** `read_turns`/`transcript_digest` are projections of `messages()` (byte-identical outputs, pinned by the existing adapter suites as golden gates); `parse_activity` deliberately stays on its record path (it needs `stop_reason` + fleet + token-folding the provider-neutral spine omits). Public seam: `read_messages(cwd, session_id) -> tuple[AgentMessage, ...]` on both filesystem adapters (mirrors `read_turns`; NOT yet on the `AgentAdapter` Protocol — promote it there only when a consumer needs it polymorphically, else generic/mewbo owe a `()`/mapping they don't have yet).

- **`AgentMessage`:** `role` (`user`/`assistant`/`tool`=result-carrier/`notification`), `content: tuple[ContentBlock,...]`, `message_id`, `tool_use_id` (message-level ONLY on notifications = the tool they report on), `parent_tool_use_id` (= Claude `sourceToolAssistantUUID`, the sub-agent→spawning-tool link), `model`, `usage`, `timestamp` (aware), `is_sidechain`, `thread_id` (= Claude `agentId`). `text()` joins text blocks only; per-call/per-result ids live on the `ContentBlock`s.
- **`TokenUsage` field = `None` means the provider didn't report it; a reported 0 is a real 0** — never fabricate. Claude sets input/output/cache_creation/cache_read (reasoning always `None`); **Codex reports usage per-SESSION not per-message, so every Codex `AgentMessage.usage` is `None`** (session totals stay on `AgentActivity`) and Codex messages have no `message_id`.
- Consumers build on the spine, never a bespoke re-parse — shipped in Wave 1: **`final_result(cwd, session_id) -> FinalResult | None` (#149)** = `final_result_from_messages(read_messages(...))`, the terminal outcome projection; **`ClaudeCodeAdapter.fleet_activity(cwd, session_id) -> list[(AgentSession, AgentActivity)]` (#173)** groups sidechain `AgentMessage`s by `thread_id` (Claude `agentId`), derives each worker's status from its own tail content-block SHAPE (assistant reply ending in a `tool_use` block = working — the spine analogue of the main-thread `stop_reason` rule, since the spine omits raw `stop_reason`), and reads identity from the sidecar `.meta.json` (degrading to a truncated first-task-prompt, never fabricated); returns `[]` when no `subagents/` dir (cheap common case). The bare `AgentActivity.active_subagents` COUNT is unchanged (still `_SubagentFleet` in `parse_activity`; fleet_activity is the itemized counterpart, not a replacement). Only the in-session sidechain fleet — a CLI `--bg` session is a separate top-level session tracked like any other.
- **`latest_todo(cwd, session_id) -> TodoList | None` (#194) is the `final_result` sibling ON the `AgentAdapter` Protocol (unlike `read_messages`, this one IS promoted there — the manager/daemon call it polymorphically across kinds).** `model.latest_todo_from_messages(messages)` is the projection, placed right next to `final_result_from_messages` and built the same way: one pass over the already-parsed spine, zero new parsing. **The load-bearing invariant a "last N turns" tail read gets wrong:** Claude's split-call Task system (`TaskCreate`/`TaskUpdate`, see below) correlates a late `TaskUpdate` against a `TaskCreate`'s server-assigned id that can sit arbitrarily far back in the SAME session — so the fold must run from session start, never a bounded tail window; a fixture pinning exactly this (`TaskUpdate` ~40 turns after its `TaskCreate`) is the regression test (`test_claude_code.py::test_latest_todo_folds_a_taskupdate_correlated_many_turns_after_its_taskcreate`). To make both call sites (this projection AND `claude_code.py::_assistant_entries`'s turn renderer) fold the identical logic without duplicating it, the create-vs-update dispatch moved OFF the adapter (`ClaudeCodeAdapter._apply_task_call`) and ONTO the board itself as `TaskBoard.apply(name, block, answered)` — the class-encapsulation principle applied to a helper that was already 100% about `TaskBoard`'s own state and had no adapter-specific dependency. mewbo (no message spine) projects the same way `final_result` does — over its own `_turn_entries` fold, keeping the last recognized entry rather than re-deriving recognition. The manager seam is `WorkspaceManager.latest_todo(workspace_id)` (resolves state → effective kind → adapter, RAISES `AgentSessionNotFound` for a sessionless workspace — the `_steer_remote`/`_steer_native` convention, not `session_controls`'s degrade-to-empty one, because a caller needs to tell "no session" (404) apart from "session exists, no todo tool called yet" (`None` → an empty `TodoListView`)); the daemon route `GET /workspaces/{id}/todo` is a thin executor-offloaded wrapper over it, mirroring the sessions routes.
- **`offline_decoration() -> list[str]` (#148) is the tools-off adapter seam, symmetric with `model_decoration`:** claude_code → `--disallowedTools WebFetch,WebSearch`; codex → sandbox network-off flags; generic/mewbo → `[]`. Composed in `_compose_launch` gated on `AgentSpec.tools_offline`, forwarded verbatim (provider boundary — Grove never decides which tools are "network").
- **`telemetry_env() -> dict[str, str]` (#170 passthrough) is the native-telemetry *enable* adapter seam, same provider-boundary shape.** `derive_env` (#176) hands over the generic OTLP endpoint/headers; *flipping the tool's own exporter on* is a per-provider flag the adapter owns: claude_code → `{CLAUDE_CODE_ENABLE_TELEMETRY:"1", OTEL_METRICS_EXPORTER:"otlp", OTEL_LOGS_EXPORTER:"otlp"}` (its usage/cost/tool metrics + `api_request` events stream to LangFuse; spans/TTFT are a beta opt-in via the agent's `env`: `OTEL_TRACES_EXPORTER=otlp` + `CLAUDE_CODE_ENHANCED_TELEMETRY_BETA=1`). **Codex → `{}`** (it configures OTel through `config.toml [otel]`, not env). generic/mewbo → `{}`. The manager injects it **only when the OTLP endpoint actually resolved** (`_launch_spec`), so a tool never enables an exporter pointed at nowhere. This is why native usage/observability needs no per-agent hand-wiring — one `telemetry.enabled` flip auto-configures Claude Code.

## Native hook push (`hook.py` + daemon ingest, #171) — hooks are ON by default now

- **`cfg.hooks.enabled` now defaults to `True`** — the native ask-time capture (#109) is the primary signal, not an opt-in. Blast radius of the flip: any suite touching `manager.create()` for a claude_code agent now writes real hook settings, so `tests/conftest.py` has an **autouse** `_isolated_agent_hook_paths` redirecting `paths.agent_sidecar_dir`/`agent_hooks_settings_path` to tmp (those read raw `platformdirs`, NOT the `user_config_path` the opt-in state fixture redirects).
- **Handler topology = dual `command` + `http` handlers on the SAME event** (not agent-hook-does-both): Claude dispatches every registered handler in parallel, so the http POST never adds latency to the agent's turn, while the `command` hook keeps writing the sidecar (offline truth). The http handler POSTs to the daemon route `HOOK_INGEST_ROUTE = "/hooks/agent-events"` (single source of truth, imported by both `ClaudeHook.settings()` and the daemon), which awaits a scoped `ActivityService.poll_once()` → collapses the poll-tick lag to an immediate SSE refresh (no new frame types).
- **Auth for the ingest route is a same-host secret file, NOT the pairing bearer** (`ClaudeHook.ensure_ingest_token()` → `hook-ingest.token`, 0600; validated by `make_require_hook_token`). The human-approval-gated pairing bearer is wrong for an automated caller firing unattended on every tool call — reuse this same-host-secret pattern for that shape of caller.
- **Stop-hook `decision:block`+`additionalContext` as a delivery slot is NOT built here** — only a verification-pinning stub. It must be empirically confirmed on the installed CC before #172 relies on it.

## Session controls + the input-affordance matrix (#178)

**`session_controls(cwd, session_id) -> SessionControls` on the adapter seam enumerates a session's controls by the CHEAPEST tier — a filesystem scan, no running session needed.** Claude: `.claude/commands/**.md` (namespaced `dir:cmd`), `.claude/skills/*/SKILL.md`, MCP from `.mcp.json` + `~/.claude.json`, model from `resolve_models`. Codex: `$CODEX_HOME/prompts/*.md`, `config.toml [mcp_servers.*]` (tomllib); no skills. generic/mewbo → empty (honest). The manager composes `models`/`current_model`/`permission_mode` (from `cfg.permission.default`) on top; `invoke_control`/`switch_model` deliver a prompt-composed `/name` / `/model <id>` through the EXISTING `send_message`/`_steer_native` path (no new dispatch, `_CONTROL_KINDS` gated → `CapabilityUnavailable` else). Wire = fetch-on-demand `SessionControlsView` + `GET /workspaces/{id}/controls` (+ invoke/model POSTs). config.py stayed UNTOUCHED — reused `cfg.permission`, `cfg.find_agent`, `AgentSpec.models`.

**Affordance matrix — what's reachable headless vs interactive-only (verify per tool release):**
- **Slash commands** (`/name`): Claude headless (stream-json, ≥2.1.181) + interactive; Codex interactive + `prompts/`. Grove delivers `/name`.
- **Skills**: Claude headless (≥2.1.181) + interactive. **Correction (2026-07-08, #190):** Codex CLI DOES have a skills system (`SKILL.md` + YAML frontmatter, same shape as Claude's) — `session_controls`' Codex arm just doesn't enumerate it yet (no skills scan in `codex.py`, unlike its `prompts/*.md` scan). See the onboarding section below for the verified directory paths; if `session_controls` ever grows a Codex skills arm, reuse `_CodexHome.base_dir()` the same way.
- **MCP servers**: enumerable both; runtime toggle/reconnect is **SDK-control-only** (Claude `mcp_toggle`/`mcp_reconnect`) / launch-only (Codex) → Grove surfaces **read-only**.
- **Model switch**: Claude interactive `/model <id>` (pane-verified) or SDK `set_model` headless; Codex `/model` may open a picker (inline-arg unverified). Grove delivers best-effort.
- **Permission mode**: Claude `/config` headless (≥2.1.181) + the `--permission-prompt-tool` (#172) answering path; Codex approvals interactive-only. Surfaced read-only (`cfg.permission.default`).
- **Auth (`/login`), `/resume` picker, Ctrl+O**: interactive-only presentation affordances — **not Grove controls** (auth is the one irreducible interactive need).

## Onboarding external tools (`onboarding.py`, #190)

**`onboarding.py` is a side-effect module like `git.py`/`tmux.py`, not an `AgentAdapter` — it writes to Claude/Codex's OWN config, never reads Grove workspace state.** `ClaudeTool`/`CodexTool` are the two `AgentTool` Protocol impls behind `grove skills install` (drops the bundled `using-grove` `SKILL.md` into a tool's skills dir) and `grove mcp install` (shells out to the tool's *own* `mcp add`, never hand-writes `.mcp.json`/`config.toml`). Path resolution reuses `_ClaudeHome.config_dirs()` / `_CodexHome.base_dir()` **directly** (same-package import, not re-derived) — the CLAUDE_CONFIG_DIR/CODEX_HOME cascade has exactly one definition.

- **User-scope skill install is gated on "has this tool been used on this host" (`user_skills_dir() -> Path | None`), never unconditional.** Claude: the first EXISTING base in `_ClaudeHome.config_dirs()` (`None` if none exist — never falls back to creating `~/.claude` from scratch, since that would be lying about detection). Codex: `_CodexHome.base_dir() / "skills"` iff `base_dir()` already exists. Project-scope is unconditional (`<repo>/.claude/skills`, `<repo>/.codex/skills`) — the user explicitly chose that repo, no detection needed.
- **Codex DOES have a skills system** (verified against `developers.openai.com/codex/skills` + `openai/codex` source, 2026-07-08): `SKILL.md` + YAML frontmatter, same shape Claude uses — `.codex/skills` (project) / `$CODEX_HOME/skills` (user, default `~/.codex/skills`). A stale note above claimed otherwise for the `session_controls` affordance matrix; corrected in place.
- **`claude mcp add` supports `--scope user|project|local` (Grove exposes the first two); `codex mcp add` has NO project-scope flag at all** — it always writes `$CODEX_HOME/config.toml` (verified against `developers.openai.com/codex/cli/reference`, 2026-07). `CodexTool.mcp_add_argv(target="project", ...)` returns `None` for exactly this reason, surfaced as an `"unsupported"` `OnboardOutcome` rather than a hand-rolled `.codex/config.toml` TOML write — the whole point of shelling out to the tool's own command is that Grove never has to reimplement its config format, so an unsupported scope is a clean no-op, not a workaround.
- **`register_mcp` shells out via `subprocess.run` referenced through `grove.core.agents.onboarding.subprocess` — patch-target trap for tests:** `subprocess` is one shared module object process-wide, so `monkeypatch.setattr("grove.core.agents.onboarding.subprocess.run", fake)` mutates the SAME attribute every other module's `import subprocess; subprocess.run(...)` resolves to (including `grove.core.git`'s own calls) for the rest of that test. A CLI-level test that also calls `detect_root` (git subprocess) in the same invocation needs its fake to pass non-`claude`/`codex` argvs through to the real `subprocess.run` — see `tests/cli/test_onboarding_commands.py::fake_mcp_add`. Engine-level tests that never touch git don't need the passthrough (`tests/core/agents/test_onboarding.py`).
- **`cli_onboarding.py` calls `onboarding.install_skill`/`onboarding.register_mcp` via a module-qualified import (`from grove.core.agents import onboarding`), not a name import** — mirrors the `tmux.py`/`manager.py` convention (`tmux.create_session(...)`) specifically so `monkeypatch.setattr(onboarding_module, "register_mcp", fake)` (whole-function fake, the `fake_tmux` style) actually reaches the CLI layer. A name import (`from ... import register_mcp`) copies the reference at import time — patching the source module's attribute afterward wouldn't affect the CLI's already-bound name.
- **The bundled skill ships as package data at `src/grove/skills/using-grove/SKILL.md`, read via `importlib.resources.files("grove") / "skills" / SKILL_NAME`** — no `__init__.py` needed under `skills/` (it's data, not an importable subpackage); hatchling's default `packages = ["src/grove"]` wheel target includes it automatically (verified: `uv build --wheel` + inspecting the zip). Never duplicate this file into this repo's own `.claude/skills/` — it would drift from the packaged copy; the packaged one IS the single source of truth, installed into *other* projects via `grove skills install`, not dogfooded into Grove's own tree.

## Session lessons

- **`AgentActivity.started_at` is the session's BIRTH (first-record timestamp), populated at zero extra parse cost (#107, 2026-07-04).** Both filesystem parsers already computed this for `SessionSummary.created_at` (`_TranscriptParser.created_at()` / `_RolloutParser.created_at()`, an in-memory scan over already-parsed records) — `activity()` now reuses the same method rather than re-deriving it. This is the seam `WorkspaceState.adopts_session` (see [grove.core](../CLAUDE.md)) compares against a workspace's own `created_at` to decide whether a *discovered* session actually belongs to it, rather than merely being the newest-touched file in the cwd. Mewbo (remote, has its own `created_at` off the wire but doesn't feed the gate) and generic (no-op) leave it `None` — a session that never discovery-adopts by construction.
- `model.py` (`AgentActivity` / `AgentSession`) is the only thing that crosses outward — keep adapters from leaking native transcript shapes past it.
- Parsing is best-effort like `peek()`: a malformed line skips, it never breaks the render loop. Booleans-as-strings is the recurring footgun.
- When a parsing fact is hard to get right, it's because the real transcript disagrees with the obvious mental model (preamble-before-cwd, user-lines-aren't-turns). Pin it against on-host JSONL, not a fixture.
