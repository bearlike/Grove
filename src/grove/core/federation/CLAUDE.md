# grove.core.federation — hub-and-spoke daemons: keys, catalog, link

> ↑ [grove.core](../CLAUDE.md) · [root](../../../../CLAUDE.md)

Several Grove daemons behind one hub. The hub holds METADATA only, which nodes exist and which node owns which workspace; every node keeps full authority over its own workspaces. No consensus, gossip, shared filesystem or live migration. The HTTP half (`/federation/*`, the forwarding proxy) is in [daemon](../../daemon/CLAUDE.md); config is `FederationConfig` in `config.py`.

- **Daemon-to-daemon identity is a mutually generated key and nothing else.** `grove node token` mints a one-time, expiring join token (only its hash is stored). The node presents it once; in the same `nodes.json` write the hub spends it and admits the node, so one token can never admit two. The hub returns a fresh secret exactly once. Human login (OIDC) is a separate concern and plays no part here.
- **The hub stores a SIGNING key, not a password hash, and that is forced.** An HMAC cannot be verified against a one-way hash of its key, so both sides keep `sha256(secret)` and sign with it. Reading `nodes.json` therefore lets you impersonate a node, exactly as reading `node-key` does; both are 0600 in the config dir beside `auth.json`. The digest still buys one thing: the secret a node was handed never sits on the hub's disk. Don't "harden" this into a hash-and-compare: that design cannot verify a signature at all.
- **The bearer MAC covers the AUDIENCE.** Both directions sign with the same per-node key, so without `hub`/`node` in the MAC a bearer a node sent the hub could be replayed at the node as the hub's. The timestamp bounds replay to `max_clock_skew_seconds` (config, not a timeout). There is no nonce, because every federation call is idempotent.
- **Every heartbeat IS a full registration.** It carries name, address, every owned workspace and draining. That makes the index converge within one beat of a create or kill, and makes a hub restart need no special case: the hub keeps nothing but keys on disk, and the next beat rebuilds what it forgot. A separate heartbeat-plus-register protocol was written first and deleted, because its "hub lost my registration" branch was the only path that ever re-sent the workspace list.
- **`PeerLink` ends on a key refusal and on nothing else.** Transport failures back off from 1 s doubling to `reconnect_ceiling_seconds`, the same as the native worker. A 401/403 is `NodeAuthRefused` and ends the loop, because no retry can fix a revoked key, and a loop that kept knocking looks like an attack. A node with no key and no join token waits rather than erroring. Line-of-sight loss is the `unreachable` state on the hub; nothing is killed.
- **`Hub.owner` answers only for a REACHABLE node.** An unreachable owner's workspace is not forwarded and not claimed by anyone else; the verb falls through to the hub's own routes, which answer honestly that the hub does not hold it. The data stays where it is.
- **Mutation-check every guard here, and expect the signature check to survive the first try.** The hub's `NodeBearer.verify` survived deletion because every test either signed correctly or used a node the hub had forgotten (refused earlier, by the lookup). Only a KNOWN node id with the WRONG key reaches it, so `test_a_known_node_id_with_the_wrong_key_cannot_register` exists for that one branch.
- **`ping` walks resolve → connect → auth and STOPS at the first failure, and every refusal is prefixed with the side that refused.** The question an operator asks is never "does it work" but "which hop is broken": DNS, TLS and a refused key take different fixes, so one red boolean costs them a round trip per guess. A node with no key fails `auth` with `node:`, while a hub that forgot the node fails it with `hub:`. `grove node join` refuses a hub URL other than the configured `federation.node.hub_url` rather than writing config, because a typo there would mint a key for a hub nothing will ever dial.
- **A project's cross-node name is its normalized remote (`ProjectIdentity`), and a path is a per-node fact.** Every clone URL form (`git@host:o/r.git`, `ssh://…:port/o/r`, `https://user@host/o/r.git`) normalizes to `host/o/r`. A path remote names nothing and yields `None`: a repo with no hosted remote cannot be federated, and saying so beats inventing a name. `RepoRegistry.root_for` matches on the remote ONLY. The default branch is carried for display and placement, but a node's clone may call it something else, and which branch a workspace starts from is the create request's own business. Each node sends its `known_identities()` on every registration, which is what lets the hub place a create only where the project already exists. Clients keep sending paths; `CreateWorkspaceRequest.project` is the hub's road, used only when `repo_root` is absent.
- **Placement filters in the order an operator debugs, and refuses naming the filter that emptied the field.** The full order is in the runtimes bullet below. "No node" is useless and "no node carries labels {residency: eu}" is a fix. Then it takes the least-loaded node by load over capacity, so a big node and a small one fill evenly; an undeclared capacity is unbounded. The hub itself is never a candidate once any node has registered, because the hub holds metadata, not workspaces. With no node at all it is a plain daemon and creates locally.
- **A reservation is separate from the registered workspace list, or the last slot is given twice.** Every heartbeat REPLACES `workspaces`, so a count bumped there is wiped by a beat landing mid-create. `pending` survives the beat, and `settle` releases it and records the new id. That second half also closes the window where a just-created workspace had no known owner until the next beat.
- **An unreachable owner is a typed 503 (`owner_unreachable`, node name and last seen), never the fall-through 404.** "The hub never heard of it" and "its node is out of sight" take opposite actions. The answer is gated by the hub's session check exactly like the forward it replaces, because who owns a workspace is not an anonymous caller's to learn.
- **The selector default comes from the PROJECT's cascade** (`scheduling.require`, committed config allowed), so an orchestrator names residency once per repo instead of per call. The request's own `selector` wins, an explicit `{}` included.
- **A node advertises the resident runtimes it configures (`RegisterRequest.runtimes`, from `GroveConfig.resident_runtimes`) on every heartbeat, and placement filters on them like any other fact.** The order is now named node → reachable → not draining → holds the project → configures the runtime → labels → capacity, so a create naming a node that lacks the driver refuses with `PlacementRefused` naming that filter, BEFORE anything is forwarded (the node never sees the request). The catalog a create form reads is `WorkspaceDefaultsView.targets`: the answering daemon first, then each reachable node on a hub. It is read-only enrichment and never a saved default, because a node can disappear between two creates. The node's runtimes come from the daemon's GLOBAL config (host configuration, like `labels`), not a project's cascade, since a node creates for every project it holds.
