# grove.core.reaper — what exists on this host against what the records entitle

> ↑ [grove.core](../CLAUDE.md) · [root](../../../../CLAUDE.md)

One concern: find Grove's own leftovers that a crash, a SIGKILL, a test run or a restart skipped, and remove them safely. It is not an exit-path cleanup (every verb already has one). It is the global pass that catches what those paths missed. `Ledger` decides entitlement (pure), each `Collector` lists one class and removes one item, `ReaperStore` remembers, and `Reaper` sequences them. It runs as the `reaper` standing watch on the existing scheduler, plus one pass in the daemon lifespan, plus `grove vacuum` by hand.

- **Any record entitles its resources, whatever its status.** A RUNNING record whose server died has nothing to find, and a destroyer must never remove what a record still names. Being conservative here costs a leak; the opposite costs a live session.
- **A collector reports what EXISTS; the ledger decides what is entitled.** `Collector` is `found()` + `remove()` and never reads a workspace record. A process is entitled by what it SERVES, read off the argv Grove itself composes: a worker's `--config <dir>/<workspace id>.json`, or an observer's `-L grove-<id>` socket (an observer only knows the 12-character socket prefix, so it is matched against socket names, never against workspace ids). Recognition never keys on a name pattern a user's own process could share, and a process serving nothing is never a candidate. The ticket's `GROVE_OWNER` env var does not exist; the argv is what Grove actually writes.
- **Two-phase, and the lock is the guarantee while the grace is the heuristic.** A candidate is MARKED on first sight and SWEPT on a later pass at least its collector's `GRACE` (a `ClassVar`, deliberately not config) after that. Each removal then holds the workspace store's `exclusive_lock` and re-reads the records under it. `create` saves its record under that same lock BEFORE starting any server or worker, so a resource a create is bringing up is always either entitled by the re-read or does not exist yet. The daemon's per-workspace asyncio lock cannot do this job, because `create` is deliberately unkeyed there (its id is minted by the call) and `grove vacuum` runs outside the daemon.
- **First-seen is DERIVED from an append-only log, never updated in place.** It is the earliest `mark` since the ref's last successful `sweep` or `clear`, so a restart between mark and sweep keeps the original sighting. **A `clear` row is what stops a vanished leak that later reappears from inheriting a stale grace**, so it is swept at once on its return. Writing one per departed mark is the price, and it is cheap.
- **A dry-run report is a current observation, not action history.** Keep the latest pass summary for `grove doctor`, but never append a `report` row for every unchanged candidate on every scheduled pass; those rows turn a harmless leak census into unbounded SQLite growth and slower first-seen reads. A new writer prunes old report rows without VACUUM, so recovery does not add a long exclusive rewrite to startup.
- **A wedged tmux server keeps its socket.** `kill-server` that fails while the socket still accepts means a live process nothing else names, so unlinking there would orphan it for good. Only a socket that refuses connections is stale. `tmux.kill_server` refuses the shared default server outright.
- **The watch belongs to the HOST, not a workspace.** Its recipient is `contracts.watches.HOST_ADDRESS` (all zeros, which no minted id can equal), it is in `HOST_KINDS` so the start-up orphan sweep does not cancel it, it never mails anything (`StillWatching` with no outcome), and `ReaperWatcher.ensure` is the one place it is registered or cancelled. Switching the reaper off has to cancel the durable row an earlier run left, which is why `ensure` takes `None`.
- **The doctor row is doctor-only.** `HostPreflight.all_checks` also feeds the create probe, so a leak row there would turn a reaper's report into a reason to refuse a create, and would add a SQLite read to every create. `cli_doctor` appends `ReaperStore.doctor_row()`, scoped `optional`.
- **A candidate inside its grace is REPORTED as `waiting`, never logged, and it counts.** Measured on first contact with the live host: the daemon's start-up pass had marked 21 candidates while `grove vacuum` printed "nothing to reap", because a marked-but-not-yet-sweepable candidate produced no row at all. Both were correct and together they read as a disagreement. `PassReport.waiting` carries `first_seen` and `sweepable_at`, `grove vacuum` prints that set before the action rows, and `found_anything` includes it, so a CI host check still exits 1 for a leak the next pass will remove. It is report-only because the action log records what a pass DID, and a waiting candidate would otherwise append a row every pass.
- **`grove vacuum` imports nothing from this package at module scope**, because every CLI invocation and every completion TAB imports the CLI module. Its `CLASSES` literal is pinned to `ResourceClass` by a test.
- **The files collector's owner is the ref's `workspace_id`, and an agent config dir holding a real transcript never becomes a ref at all.** `agent-config/<ws>` is where a container's transcripts live, so `kill` keeps it and the reaper may take it only when no `projects/**/*.jsonl` exceeds `TRANSCRIPT_FLOOR` (1 KB). The floor comes from a measurement, not a guess. On 2026-10-21, 8,175 dirs held 571 MB and 353 of them held a transcript. The 89 transcripts over 1 KB sat in only **18** dirs, so the rest were copies of a seeded `.claude.json` plus empty session stubs. #988 read the 89 as a dir count; count dirs, not files, when sizing a keep-rule. A dir that is kept is left out of `found()` and listed on `kept`, and `remove` checks the floor again at the moment it acts, so a transcript written after the mark still wins. A sidecar is keyed by session, so the usage store maps it to a workspace and an unknown session stays owned by its own id, which the ledger matches against each record's `agent_session_id`. `config.json.bak*` is never in reach, because `remove` refuses any path outside the six accessor directories.
- **A collector looks its `paths` accessors up BY NAME at call time.** A tuple of the functions themselves binds them at import, before the autouse redirect, so the test suite listed the developer's live state dir. Only a red spot test showed it.
- **Out of scope here, by decision:** pruning transcripts (usage retention, #938), the SQLite stores, and docker, worktree and remote collectors, which are later classes against the same Protocol.
